# 网关管理就绪与账号启动

账号验证迁移不能沿用“全部账号启动结束才开放私有 IPC”的条件。ClawBot 的首次启动会等待二维码和配对码，而这些交互本身需要管理客户端；ICQQ 的启动则通常只发起登录。宿主必须支持两者，不能修改平台 SDK 的完成语义来掩盖等待。

## 生命周期边界

- 网关管理就绪：配置和插件已加载，私有 HTTP/IPC 已可用，管理服务已绑定该进程身份。此状态不表示平台账号在线或所有协议出口已经就绪。
- 账号启动：独立的受管任务，状态通过账号事实表达。保留 `Account.start()` 等待自身启动监听器与协议启动的契约。
- 旧 `BaseApp.start()`：继续等待账号启动任务，避免改变嵌入式调用者的完成条件。独立网关使用明确的分阶段启动入口，不能通过监听端口事件抢先报告成功。
- 停止：在任何异步清理前使本轮启动失效并发出取消；同一停止任务只清理一次。迟到任务不能启动下一账号、下一适配器、下一启动监听器，不能重新监听端口或把宿主改回已启动。

需要为 BaseApp、Adapter 队列和 Account 启动逐级传递运行代次及取消信号。普通账号启动失败仍允许其他账号获得启动机会，但取消不是普通失败，必须退出旧队列。通用 `emitAllAwaited` 的清理聚合语义不变，启动使用专门的可取消遍历。账号停止后其路由已关闭、监听器已删除，重启应创建新对象，不复用已释放对象。

不响应取消的第三方任务不能被宣称为已经静止。先执行停止清理，最终以受管子进程和进程树的实际退出证明释放启动权限；不能无条件等待第三方 Promise 而永久阻塞停机，也不能因为丢弃 Promise 引用就认定已回收。

## 验证挑战与提交

网关内存保留每次挑战的独立 UUID、有效期及适配器提示；同平台/账号/类型的新请求替换旧挑战，但旧完成回执不能删除新请求。最多 20 条，30 分钟有效，单条 JSON 上限 1 MiB，用于容纳二维码。提示快照与原业务对象隔离，验证码和 ticket 的提交内容不进入该存储。

后续提交必须同时绑定管理/网关实例、配置版本、挑战 ID 和操作 ID。请求短信和提交验证都是外部副作用，应先持久记录派发意图，再在网关按账号串行核验当前挑战。操作记录不得保存验证码、密码或 ticket 明文；确认丢失保留 unknown，不自动重发。SDK 方法返回最多证明调用已被接受，不能证明账号登录成功。

## 验收

1. 首个账号或适配器启动挂起，stop 完成后释放它，后续账号/适配器不得启动。
2. 生命周期启动钩子挂起时 stop，随后释放钩子，不得监听 HTTP；停止后 `isStarted` 不得恢复为 true。
3. 首个账号启动监听器或协议挂起时 stop，后续监听器/协议不得执行，迟到完成不覆盖停止状态。
4. 同时调用 start 或 stop 共用本轮任务，停止清理不重复。
5. 模拟扫码账号保持等待时，独立网关仍能管理、读取挑战和提交；完成挑战后账号和协议按原契约启动。
6. 普通账号失败不阻止其他账号启动；取消必须停止整个旧队列。
7. 实际子进程退出证明覆盖不响应取消的任务；模拟账号不等同于真实 ICQQ 或微信登录验收。

当前已实现挑战存储与 GatewayApp 事件收集，以及 Account 启动监听器、Adapter 启动批次的停止取消边界：旧等待结束后不再推进后续工作，单账号 stop 不取消无关独立启动批次。第三方挂起任务仍保持未结束事实，不以批次失效冒充回收。

BaseApp 已共用启动和停止任务，并在停止时同步取消本轮启动；生命周期钩子与适配器之间检查取消，HTTP 监听使用 Node 的原生取消信号覆盖尚未完成绑定的窗口。取消的旧启动不重复取得清理权，也不把宿主改回已启动。此机制不表示不响应取消的第三方任务已经退出。

分阶段启动已接入独立网关：管理入口完成生命周期与 HTTP 监听后返回共享账号任务，网关建立 IPC 后继续观察该任务。旧 `BaseApp.start()` 仍等待同一个账号任务，`isStarted` 与协议 readiness 不提前变更。停止引起的账号取消由唯一停止路径处理，不重复发送启动失败。MCP 仅能连接 ready 协议，并在会话中再次核查，禁止迟到调用结果冒充成功。

受管启动还启用独立的协议路由就绪闸门：协议工厂和异步启动期间注册的 HTTP/WS 路由捕获所属协议的状态，未 ready 时返回 503。平台回调不带协议条件，等待登录期间仍可访问；账号原有路由作用域继续负责清理。普通嵌入式启动不自动启用这个闸门，保留直接调用协议启动方法的既有行为。

本轮通过实际构建的网关子进程验证：账号等待期间收到管理 ready 且消息调试 IPC 可用；协议异步启动期间返回 503、平台 callback 返回 200；释放等待后协议返回 ready；等待期间停止正常退出且不重复报告 START_FAILED。全仓构建、818 个测试文件（5869 项通过、1 项因非 Linux 环境跳过 systemd-analyze）及 41 个发布包检查通过。这些是本地测试扩展与构建产物的证据，不代表真实 ICQQ/ClawBot 登录已验收。

验证 IPC 已接通挑战列表和受控提交，网关驱动只向当前实例派发，帧同时绑定配置版本。列表最多 20 条、每条请求最多 1 MiB，完整列表帧也有总字节上限。提交依据原挑战声明的输入、快捷操作和短信能力校验，不能由客户端指定另一个平台或账号。同账号的验证副作用不并发；相同操作 ID 只返回原结果，内容冲突拒绝。进程内收据仅保留随机密钥 HMAC 摘要和结果，最多 1024 条、不淘汰已派发记录；关闭或 SDK 调用后异常返回 unknown，不以调用返回冒充登录完成。短信请求成功保留挑战，普通提交只完成原挑战 ID。

实际构建网关已通过“账号等待 → IPC 查询挑战 → 提交原挑战 → 协议 ready”的测试，以及同操作回放、挑战替换、同账号并发、账号对象替换和关闭后的未知结果测试。最终主包构建、820 个测试文件（5887 项通过、1 项平台检查跳过）及 41 个发布包检查通过。测试运行使用仓库固定 pnpm 9.15.9，未修改本机 Corepack 全局配置。MCP 管理测试已改为只读等待协议实际 ready，不再把网关管理握手当作协议就绪。

持久化提交及 CLI/TUI/Web 验证界面仍需完成，因此上述执行器目前只暴露给管理服务私有 IPC，没有新增绕过持久化回执的公开提交入口，旧验证路由暂不删除。下一步管理端必须先持久化意图再派发、绑定设备 owner、跨重启将未确认操作归为 unknown，并使用独立受限密钥 HMAC 绑定低熵答案，不能持久化普通验证码 hash。尚未禁止释放后的 Account 被新的直接 start 调用复用；旧 BaseApp.reload 与 stop 的竞争也仍待处理（独立 GatewayApp 已禁止热重载，使用管理服务切换实例）。这些剩余项必须与宿主生命周期一同完成验收。
