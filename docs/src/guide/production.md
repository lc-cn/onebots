# 生产就绪功能

OneBots 提供了完整的生产级功能，包括安全性、稳定性和可观测性，确保系统可以在生产环境中稳定运行。

## 安全性功能

### 速率限制 (Rate Limiting)

防止 API 滥用，保护服务器资源。

**特性**:
- 基于时间窗口的速率限制
- 支持自定义键生成
- 自动设置响应头（X-RateLimit-*）
- 集成安全审计日志

**默认配置**: 每个 OneBots 实例按客户端 IP 计算 1 分钟 100 次普通请求。`/health`、`/ready`、`/metrics` 完全跳过通用限流，因此探针不会因页面轮询、Webhook 或登录尝试返回 429；管理登录也不消耗该共享预算，而是进入下述更严格的失败专用边界。自定义 `path` 前缀会进入这些精确端点的匹配。

管理登录的失败专用限制为：同一来源在 5 分钟内允许 10 次失败的鉴权码或用户名密码尝试，成功登录不计入该窗口，实例切换等前置验证失败也不会误伤凭据预算。超过限制时服务返回 HTTP 429、`Retry-After` 和剩余秒数；Web 登录页会直接显示可重试时间并保留已有会话。通用与登录限流器都由每个应用实例独立持有，并在生命周期清理时释放，嵌入式多实例不会互相消耗预算。

第三方宿主使用 `createRateLimit()` 自定义键时，键会作为 `Map` 中的不透明字符串处理；`__proto__`、`constructor` 等名称不会访问或修改对象原型。返回的中间件带有 `close()`，宿主应在自身生命周期结束时调用，以释放清理定时器和内存计数。

**自动启用**: 已在 `BaseApp` 中自动集成，无需额外配置

### 安全审计日志

记录所有安全相关事件，满足合规要求。

**特性**:
- 认证成功/失败记录
- 无效令牌记录
- 速率限制触发记录
- 可疑请求记录
- 错误事件记录
- JSON Lines 格式日志
- 按日期分割日志文件

**日志位置**: `{dataDir}/audit/security-audit-{date}.log`

**自动启用**: 已在 `BaseApp` 中自动集成

每个 `BaseApp` 都绑定自己的审计目录与写入器。认证失败、无效令牌和限流等辅助事件会沿当前请求写入所属实例；停止一个嵌入式应用不会关闭或重定向其他仍在运行实例的审计流。第三方宿主可用 `createSecurityAudit()` 创建同样的实例级中间件，并在自身生命周期结束时等待其 `close()`；旧的 `initSecurityAudit()`、`securityAudit()` 与 `closeSecurityAudit()` 仍供单一全局集成兼容使用。

无效令牌审计与令牌生成、刷新、撤销日志不会保存 token 原文或明文前缀。需要关联同一进程内的事件时，日志只记录使用进程随机密钥生成的 16 位 HMAC 指纹；密钥不会写盘，进程重启后指纹会变化。该值只用于排障关联，不能作为令牌身份或鉴权证据。

### 管理面鉴权边界

doctor 的受保护管理响应统一限制为 4 MiB，覆盖用户名密码登录、已认证身份、系统配置状态、适配器与账号能力，以及扩展运行证据。读取器会先检查 `Content-Length`，并继续按实际流式字节数计数；超限时立即取消正文并让对应检查失败。匿名管理检查与会话登出不需要正文，会直接取消响应流。这样即使插件生成异常巨大的能力清单或端口上的进程持续发送数据，诊断也不会无界积累响应内存；公开 `/health`、`/ready` 仍使用更严格的 64 KiB 上限。

`onebots doctor` 不会因为配置端口可连接就立即发送管理凭据。它先用禁止缓存且禁止重定向的公开 `/health` 证明应用名、当前 CLI 版本与健康语义，再要求 `/health`、`/ready` 的应用、版本和 `instance_id` 一致；托管服务还必须匹配本地 `service.json` 计算出的 `runtime_contract_id`。任一证据缺失、冲突或来自重定向后的响应时，报告新增 `management-identity` 错误并跳过登录、Bearer 请求与带 token 的 WebSocket 握手，避免把配置中的 token、用户名或密码误发给占用端口的其他服务。身份成立后，doctor 还会从不含 Router 前缀的 Web origin 验证有界 HTML、`no-store`、`no-referrer` 和当前前缀元数据，并把结果记录为 `management-page`；通用 HTTP 200 页面或旧前缀不能充当管理页证据。所有管理检查和临时会话注销完成后，doctor 会再次执行无凭据 `/health`，并逐项核对应用、版本、`instance_id` 与 `runtime_contract_id`；诊断期间发生进程重启、端口接管或最终探针不可达时，`management-instance` 会拒绝接受跨实例拼接的管理页、配置、扩展、能力和运行态证据。readiness 因账号或协议故障返回 503 时，只要身份链仍完整，管理诊断会继续定位具体出口。服务启动、重启和更新后的上线门禁复用同一探针函数，因此也不会用其他地址的健康响应证明目标端口已经接管。公开身份不是针对恶意同机进程的密码学证明，生产主机仍应使用独立服务用户和操作系统权限隔离。

`/api/*`、根管理 WebSocket `/` 与终端 WebSocket `/api/terminal` 使用同一组动态认证材料。普通管理 HTTP 只从 `Authorization: Bearer <token>` 读取凭据；`/api/auth/login` 可以在 JSON body 中提交顶层 `access_token`，也可以用用户名密码换取会话 token。日志、账号验证和消息调试 SSE 使用带 Authorization header 的 Fetch 流，不会把长期 token 写进 URL，并由同一客户端统一处理分帧、取消与有界重连。客户端按解码前字节将每个 SSE 事件限制为 1 MiB；连接总流量不受影响，但单个事件超限会取消正文、报告明确错误并停止自动重连，避免持续连接反复接收畸形大事件。只有浏览器 WebSocket 握手可通过 `Authorization` 或 `?access_token=<token>` 传递，因为原生 WebSocket API 无法设置请求头。未授权 WebSocket 会在协议升级前返回 HTTP 401，不会先建立连接再关闭，因此无法收到包含完整配置的 `system.sync`。

Web 的手动鉴权码、用户名密码、`?access_token=` 引导登录和 refresh token 续期在发送任何凭据前，都会先以 2 秒无凭据、禁缓存且禁止重定向的 `/health` 请求验证应用、版本、`instance_id` 与 `runtime_contract_id`。证据无效或不可达时只显示诊断，不会发出包含秘密的认证 POST。身份成立后，请求携带预期实例；登录与刷新端点在凭据校验或续签前拒绝已经切换的实例，并让全部成功或失败回执携带不可缓存的完整实例身份。浏览器仅在回执仍与前置探针完全一致时提交新会话，认证 POST 本身也禁止重定向。因此错误端口、通用成功页、跨实例反向代理或切换后的旧页面不能获得可被 Web 接受的认证结果。公开身份不是密码学证明，恶意同源服务仍需由 TLS、独立服务用户与操作系统权限隔离。

无效链接不会覆盖已有 token；已有会话会继续使用，尚未登录时则回到登录页说明凭据无效。每次认证交换和主动登出拥有独立的 5 秒请求边界，超时、网络不可达、主动取消与凭据拒绝使用不同语义；慢代理不能让路由守卫、登录按钮或退出操作永久挂起。登出即使无法联系服务端也会清理浏览器本地凭据，服务端会话则在自然过期后失效。无论链接验证结果如何，下一次导航都会先从地址栏移除鉴权码。管理 HTML 还会同时通过 `Referrer-Policy: no-referrer` 响应头和前置的 referrer meta 禁止发送来源地址，因此脚本与样式在前端执行之前加载时，也不会把含 token 的入口 URL 复制到 `Referer` 请求头。建议人工集成优先在登录页输入鉴权码；根管理 WebSocket 的查询参数只用于无法设置 `Authorization` 请求头的客户端。

通过“保存并应用”轮换 `username`、`password` 或 `access_token` 后，HTTP 登录和 WebSocket upgrade 会立即使用新值。已有访问与刷新令牌会全部撤销，已连接的根管理与终端 WebSocket 会以策略违规状态关闭；日志、账号验证和消息调试 SSE 也会同步停止心跳并结束响应，旧会话无法在撤销后继续接收敏感事件。Web 会用当前本地凭据尝试重连，旧凭据被明确拒绝后回到登录页。只修改账号、协议或日志级别不会中断管理会话。正常停机与启动失败回滚复用同一管理流注册表，逐个释放定时器和响应；单个连接清理失败不会阻止其他连接关闭，最终错误会聚合保留失败证据。

用户名密码签发的会话 token 自然过期后，已建立的根管理与终端 WebSocket、日志、账号验证和消息调试 SSE 也不能继续被动接收数据。服务端每 30 秒重验一次长连接凭据，最迟在下一次检查时停止心跳并关闭连接。配置文件或 `ONEBOTS_ACCESS_TOKEN` 提供的部署级 token 没有会话过期时间，因此会保持连接，直到凭据轮换、服务停止或网络断开。

旧版客户端仍可通过根管理 WebSocket 的 `system.input` 动作向进程 stdin 提交一行字符串。服务端会返回可关联的 `system.input.result` 回执，拒绝非字符串载荷，并且不会为单条消息伪造 stdin 的全局 `end` 事件；同一连接可以连续提交输入，进程内其他 stdin 消费者也不会因首条远程输入被提前关闭。新版 Web 控制台使用隔离的 `/api/terminal` PTY，不依赖这条兼容路径。

`/api/terminal` 会在调用原生 PTY 前解析完整 JSON 契约：输入必须是字符串且单次不超过 64 KiB，行列尺寸必须是 `1` 到 `1000` 的安全整数，畸形 JSON、未知动作和无效字段都会收到结构化错误而不会进入原生模块。PTY 自然退出时，服务端先向所有终端客户端发送 `exit`，再正常关闭对应 WebSocket；Web 控制台因此会进入统一的断线重连路径并创建新 PTY，而不会停留在一个仍显示为连接但已无终端进程的失效会话中。

Web 控制台的终端连接还使用单一代次与单一重连定时器。手动重连会先移除旧 socket 的回调再关闭它，旧连接迟到的 `close` 不能再创建额外连接；离开终端页面会同时取消待执行的重连并释放当前 socket，三秒后不会在后台重新生成孤儿终端会话。

终端自动重连会区分关闭原因。网络中断、服务重启和 PTY 正常退出仍按三秒间隔恢复；服务端用 `1008` 表示会话过期或管理凭据轮换时，页面会明确提示重新登录并停止携带同一失效凭据循环请求。用户更新凭据后仍可手动连接。

日志、账号验证与消息调试使用的鉴权 SSE 也区分最终拒绝和暂时故障。`authFetch` 完成一次令牌刷新后仍收到 HTTP 401 或 403 时，事件流会取消响应正文、报告一次错误并停止重试；网络异常和 HTTP 5xx 仍按配置间隔恢复。即使浏览器跳转被嵌入容器延迟或阻止，失效管理凭据也不会形成后台请求循环。

这三类受保护 SSE 共用同一响应契约：`Cache-Control: no-store, no-transform` 禁止浏览器和中间层存储或改写日志、登录验证与消息载荷，`X-Accel-Buffering: no` 提示兼容的反向代理立即转发事件而不是攒批。连接级 keep-alive 与心跳保持不变，因此安全缓存策略不会牺牲实时性。

账号登录验证面板还把待处理列表、SSE 和平台写操作闭合为同一实例快照。待处理列表通过标准响应头声明应用、版本、`instance_id` 与运行契约，并在每次刷新时完整替换旧列表，已解决或过期的请求不会因前端合并而残留。每条 SSE 连接在任何验证请求或清除事件前先发送身份事件；重连到新实例时，Web 会清空旧卡片并重新读取快照。发送短信和提交滑块、扫码确认或验证码时，请求携带该快照的预期实例；服务端在解析目标或调用适配器前拒绝实例漂移，响应则必须在标准头和 JSON 回执中同时证明处理实例。服务重启、反向代理跨实例分流或旧页面因此不能把登录凭据提交给不再拥有该待处理验证的进程。

### 令牌管理

完整的令牌生命周期管理。

**特性**:
- 令牌生成和验证
- 令牌过期检查
- 令牌刷新机制
- 自动清理过期令牌
- 令牌撤销功能

**使用示例**:

```typescript
import { TokenManager, createManagedTokenValidator } from '@onebots/core';

// 为当前宿主创建独立令牌管理器
const tokenManager = new TokenManager({
    defaultExpiration: 3600000, // 1小时
    autoRefresh: true,
});

// 创建令牌验证中间件
const tokenValidator = createManagedTokenValidator(tokenManager);
```

访问令牌和刷新令牌按各自的过期时间清理。访问令牌自然过期或被验证为过期时，仍在有效窗口内的刷新令牌可以继续换取新会话；只有显式撤销、凭据轮换或刷新令牌自身过期才会终止该刷新窗口。清理在新会话签发时按需执行，不创建后台定时器。`App` 自动持有独立的 `app.tokenManager`，同一进程内的多个网关不会改写彼此的会话管理器；`initTokenManager()` 与 `getTokenManager()` 仅为有意使用单一全局实例的旧集成保留。

### HMAC 签名验证

防止请求篡改和重放攻击。

**特性**:
- 支持多种 HMAC 算法（默认 SHA256）
- 时间安全比较
- 防止重放攻击

### 动态对象路径边界

第三方扩展处理外部提供的字段路径时，可使用 `@onebots/core` 导出的 `getValueOfObj` 与 `setValueToObj`。两者只读取或穿过对象的自有属性，并拒绝空路径段以及 `__proto__`、`constructor`、`prototype` 等原型链保留名称。非法路径会抛出 `SyntaxError`，写操作不会修改目标对象；扩展应把该错误转换为面向调用方的参数校验失败，不要改用不受约束的动态属性遍历。

合并外部配置时应使用同包导出的 `deepMerge`。它只合并来源对象的可枚举自有字段，并会在修改目标对象前递归拒绝上述原型链保留名称；数组仍按原有顺序合并去重。这样畸形的账号或协议配置会整体失败，不会留下部分合并结果。

需要保存配置快照时使用 `deepClone`。它保证成功返回的是结构化克隆的独立副本；函数、WeakMap 等无法安全克隆的值会直接抛错，不会退回调用方持有的原对象。账号编辑也始终先克隆当前配置再构造候选，因此候选校验、运行态切换或写盘开始前不会改动在线配置。

## 稳定性功能

### 熔断器模式

防止级联故障，提高系统韧性。

**特性**:
- 三种状态：关闭、开启、半开
- 基于失败次数和错误率的触发
- 自动恢复机制
- 状态监控和统计

**使用示例**:

```typescript
import { CircuitBreaker } from '@onebots/core';

const circuitBreaker = new CircuitBreaker({
    failureThreshold: 5,        // 失败阈值
    resetTimeout: 60000,        // 重置超时（60秒）
    halfOpenMaxCalls: 3,        // 半开状态最大调用数
});

// 使用熔断器执行操作
try {
    const result = await circuitBreaker.execute(async () => {
        return await externalService.call();
    });
} catch (error) {
    // 处理错误
}
```

### 重试机制

自动处理临时故障，提高成功率。

**特性**:
- 指数退避策略
- 随机抖动（防止惊群效应）
- 可配置重试次数和延迟
- 智能错误判断（只重试网络错误）

### 连接池

优化资源使用，提高性能。

**特性**:
- 连接复用
- 最大/最小连接数控制
- 空闲连接自动清理
- 连接验证
- 等待队列管理

## 可观测性

### 性能指标收集

自动收集系统性能指标。

**特性**:
- 计数器（Counter）
- 仪表（Gauge）
- 直方图（Histogram）
- 标签支持
- 时间窗口统计
- 自动清理过期数据

**自动启用**: 已在 `BaseApp` 中自动集成

每个 `BaseApp` 持有独立的 `MetricsCollector`，HTTP 请求、响应时间与错误计数只会出现在所属实例的 `/metrics`，停止一个嵌入式应用也不会重置其他实例。宿主可通过 `app.metrics` 读取该实例的性能数据。直接使用 Koa 中间件时，可把自建的 `MetricsCollector` 传给 `metricsCollector(collector)`；不传参数仍使用导出的全局 `metrics`，兼容原有单应用集成。

### Prometheus 指标导出

标准格式的指标导出，可直接接入 Prometheus + Grafana。

**端点**: `GET /metrics`

**指标包括**:
- 应用信息（版本、运行时间）
- 与 `/ready` 完全一致的当前就绪结论
- 内存使用（RSS、堆内存）
- 适配器、账号和协议出口状态
- 配置同步状态及其具体分类
- 管理 WebSocket 活跃连接、连接上限与满载拒绝次数
- HTTP 请求指标（请求数、响应时间、错误率）

**使用示例**:

```bash
# 访问指标端点
curl http://localhost:6727/metrics

# 配置 Prometheus
scrape_configs:
  - job_name: 'onebots'
    static_configs:
      - targets: ['localhost:6727']
```

### 健康检查端点

支持 Kubernetes 部署的探针。

**端点**:
- `GET /health` - 存活探针（liveness probe）
- `GET /ready` - 就绪探针（readiness probe）

**功能**:
- `/health`: 基础健康检查
- `/ready`: 检查服务、账号和每个协议出口是否就绪

宿主配置 `path: gateway` 时，所有 Router HTTP 路由统一挂载到规范前缀 `/gateway`，因此探针地址是 `/gateway/health` 与 `/gateway/ready`，管理 API 也位于 `/gateway/api/*`；根路径不再暴露这些 HTTP 路由。前缀可写成 `gateway` 或 `/gateway/`，启动时都会规范化为 `/gateway`。包含 authority、路径穿越、编码分隔符、查询串或 fragment 的值会被配置校验拒绝。WebSocket 使用独立的绝对 pathname，不继承 HTTP 前缀；管理 WebSocket 仍位于 `/`。`onebots status`、`doctor` 与服务上线验证会读取同一配置并自动使用规范后的 HTTP 地址。随主程序发布的 Web HTML 会在每次页面请求中注入当前进程的非敏感前缀元数据，并禁止缓存这份入口；登录、配置、扩展、探针和协议出口链接会自动使用它，无需用 `VITE_API_BASE` 重新构建 Web 包。构建期显式配置仍拥有最高优先级，畸形运行时元数据则退回同源根路径，避免把 Bearer 请求导向其他 origin。

普通管理 API 响应统一声明 `Cache-Control: no-store`，包括登录、令牌刷新、鉴权失败、账号与适配器清单、系统信息、配置正文和扩展状态。Web 管理端也为这些请求主动设置 `cache: no-store`，避免浏览器或错误配置的中间缓存复用旧运行态、旧配置或包含凭据的响应。日志、账号验证和消息调试 SSE 使用 `no-store, no-transform` 并关闭兼容反向代理的响应缓冲，避免敏感事件被存储、改写或延迟攒批。

公开 `/health`、`/ready` 与 `/metrics` 同样声明 `no-store, no-transform` 和 `X-Content-Type-Options: nosniff`，使探针与采集器读取当前进程的原始证据，而不是缓存或中间层改写后的响应。`/metrics` 还固定使用 Prometheus 文本格式的 `text/plain; version=0.0.4; charset=utf-8`，部署验证不再依赖 Web 框架对字符串正文的 MIME 推断。

`/health` 的 `application` 与 `version` 表示实际运行的 `onebots` 主程序包，`core_version` 单独表示 `@onebots/core`。`instance_id` 在每次进程启动时生成，`started_at` 保留该进程的启动时间，可用于证明端口已经由新实例接管。Prometheus 的 `onebots_info` 使用主程序版本，`onebots_core_info` 使用 Core 版本；Web「系统信息」也会分别展示两者，避免升级后把依赖版本误认作在线应用版本。

`/ready` 同时携带与 `/health` 一致的 `application`、`version`、`core_version`、`instance_id` 和 `started_at`，因此单独保存一份就绪响应也能证明它属于哪个 OneBots 进程，而不是代理或其他应用返回的同名布尔值。其 `summary` 给出账号与协议实例总数、在线/就绪数量以及 `accounts_without_protocols`；每个平台也会列出缺少协议出口的账号数，以及协议的 `ready`、`unavailable` 与 `total`。即使平台账号已经 online，只要任一协议 `start()` 失败或任一账号没有协议出口，端点仍会返回 HTTP 503。响应中的 `config.status` 与 `config.in_sync` 还会证明磁盘配置是否就是当前运行版本；外部修改、不可读文件或等待重启的宿主配置会撤销 readiness。首次启动尚未配置账号时，管理面保持 HTTP 200 以便继续配置，但响应包含 `configured: false`，doctor 会把它明确标为警告。

由 OneBots 运行入口启动的 `/health` 与 `/ready` 还会发布相同的 `runtime_contract_id`。它是配置路径、实际插件选择、Node、CLI 入口和工作目录经过规范化后的 SHA-256 摘要，响应不直接包含原始路径或参数。`doctor`、`status` 以及 start/restart/update 的上线门禁会用本地 `service.json` 独立计算期望值；字段缺失、两份探针不一致或摘要不匹配都会失败。因此重新安装定义后仍在运行的同版本旧进程、错误工作目录启动的进程，或未采用新插件选择的实例，不再能仅凭版本和端口冒充当前受管服务。

Web 顶栏每 5 秒读取同一份 `/ready` 语义证据，区分「生产就绪」「待配置」「未就绪」和探针证据无效，而不再仅凭账号 online 数量显示绿色状态；点击状态可进入「系统信息」查看探针。系统页同时校验 `/health` 的应用身份、版本、实例与运行契约标识，以及 `/ready` 自己的应用与实例身份、HTTP 状态、布尔结论、账号/协议计数和配置状态是否互相一致；两份响应的应用、版本、`instance_id` 或 `runtime_contract_id` 不同会显示“证据冲突”。因此代理返回的空 200、其他应用的响应、跨实例分流、旧启动契约或矛盾 JSON 都不会被误报为可用。系统页的自动刷新每 10 秒同时更新受保护的进程信息与这对公开探针；自动周期和手动“刷新”会合并进行中的服务检查，慢请求不会叠加，5 秒未完成的系统信息与鉴权刷新会释放本轮任务供下一周期重试。各页面只启动自己实际使用的资源轮询，避免系统页、顶栏与机器人页重复请求同一清单。

热重载配置期间 HTTP 存活探针继续返回成功，但 `/ready` 会立即返回 HTTP 503 并声明 `reloading: true`，直到新账号与协议出口完成启动或旧配置完成回滚。首次进程启动仍会保留账号或协议启动失败的运行态，便于从管理面和 readiness 定位凭据、权限或平台故障。同一适配器下的账号会逐个独立尝试启动：单个账号失败不会阻止后续账号上线，每项失败日志都带平台与账号标识；多个失败最终聚合返回，不会丢失较晚账号的证据。账号构造和启动期间通过共享 Router 注册的 HTTP 与 WebSocket 路径会自动归属该账号；停止、删除、热重载或候选回滚会先撤销这些路径并终止连接，旧处理器不会继续抢占新账号的同名路径。作用域关闭后才发生的迟到注册也会立即撤销，第三方扩展无需操作 Router 内部栈。全局 `timeout` 同时约束每个账号的登录监听器与协议出口启动；超过边界会中止传给扩展的 `AbortSignal`，将正在启动的协议标记为失败，并阻止迟到完成覆盖停止或失败状态。Core 的 `ConnectionManager` 会把信号继续传给连接工厂，并以连接代次阻止取消后的成功回调或重试；Discord、Slack、Telegram、LINE、飞书、钉钉、Facebook Messenger、邮件、Matrix、Zulip、KOOK、黑盒语音、WhatsApp 与微信 ClawBot 已在账号边界消费该信号，取消时关闭未完成连接、令牌与 Graph 请求、SMTP/IMAP、Event Queue、`/sync`、Gateway 与 WebSocket 握手、扫码或轮询，并忽略迟到身份响应。其他扩展也应监听该信号以取消底层网络工作；无法响应信号的同步阻塞代码仍只能由进程监督器处理。“保存并应用”则采用严格事务，任一适配器、账号或协议异步启动失败都会让应用操作失败，清理候选运行态并重新构造旧配置。旧运行态尚未完整停止时不会开始切换；若候选清理或旧运行态恢复也失败，最终错误会同时保留原始应用错误和回滚错误，不会把部分成功标记为已应用。外层配置保存边界随后恢复磁盘旧版本；回滚前会重新核对候选文件的真实路径、设备、inode、内容与权限。若另一进程已在重载期间写入新配置，失败响应会同时保留应用错误与配置冲突证据，并保留磁盘上的新文件，而不会用更旧的备份覆盖它。即使运行态处理已经成功或只要求重启，返回响应前仍会执行同一重验；发现磁盘漂移时返回可重试冲突且跳过远端备份，避免把运行态与持久化状态不一致误报为保存成功。并发热重载会被拒绝，防止两次配置切换交错覆盖。Prometheus 的 `onebots_reloading` 可用于记录和告警持续时间异常的重载。

部署或更新后可运行 `onebots doctor -c config.yaml --json --strict` 作为自动化门禁。JSON 使用带 `schemaVersion` 的稳定报告 envelope，并记录 `generatedAt`、当前 OneBots CLI 身份与版本，以及本次实际采用的配置路径、API/探针地址 `target.baseUrl`、Web 管理地址 `target.webUrl`、数据目录、解析后的数据库路径、扩展根、模块解析目录、服务范围和模式、适配器与协议列表及各自来源；CI 留档因此可以直接证明一次检查针对哪套安装、配置和网络入口，无需解析人类可读消息。地址配置无法解析时两个字段为 `null`，具体原因保留在 `gateway-address` 检查中。显式配置路径使前台或 Docker 部署执行独立配置诊断；若该路径就是托管服务保存的配置，doctor 仍会核验服务是否运行。独立诊断会像前台监听器一样让当前进程中非空的 `PORT` 覆盖 `config.port`，`onebots send` 也使用同一优先级，因此 Hugging Face 等托管环境不会探测或调用错误端口；无效的 `PORT` 会作为地址配置错误进入报告。已安装守护服务仍以保存的配置为准，不会把调用 doctor 时一次性的 shell 环境误认为服务定义。doctor 会把 `/health` 的在线主程序版本与当前 CLI 版本对比；不一致或旧端点无法证明版本时产生警告，严格模式会因此失败，能发现依赖已更新但旧进程尚未重启或命令入口指向另一套安装。默认模式仍允许首次配置流程继续，将未配置账号、服务未安装或已停止、无法完成合法管理凭据探测等状态保留为警告；`--strict` 会让任一警告同时令 JSON `ok` 为 `false` 并返回退出码 `1`。配置端口可连接时，doctor 会同时探测这两个端点；非 2xx、非 JSON、`status` 不是 `ok`、`ready` 不是 `true`，成功的 readiness 没有声明 OneBots 身份，或者两份探针来自不同应用版本或实例，都会让检查失败。独立的 `probe-instance` 检查在文本与 JSON 报告中保留成对身份结论。`/ready` 失败时，报告会列出在线账号、就绪协议数量、对应的未就绪平台以及缺少协议出口的账号，避免只看到一个没有上下文的 HTTP 503。Prometheus 可通过 `onebots_accounts_without_protocols` 为这类配置缺口设置告警。

若已安装服务的 `service.json` 被截断、无法读取或结构损坏，doctor 仍会生成完整 JSON 报告，将 `target.service.mode` 标记为 `invalid`，并以 `service-metadata` 错误阻止部署门禁通过。公开错误只包含元数据路径，不回显原始 JSON 片段；重新执行 `onebots install` 可按当前配置生成新的服务定义。在 POSIX 系统上，独立的 `service-metadata-mode` 还会验证这份运行契约没有向其他用户开放或允许同组修改；用户级 `--fix` 可恢复安装器约定的 `0600`，系统级元数据则只报告并交由管理员处理。

首次安装服务时，最终状态目录以 `0700` 创建，父级 XDG、Library 或系统目录仍保留平台默认权限；`service.json` 继续使用 `0600`。该目录还包含 launchd、Windows runner 与服务日志，因此 doctor 的 `service-permissions` 会把其他用户可访问或同组可修改判为错误，用户级 `--fix` 可收紧为 `0700`。仅允许同组读取或遍历时保留警告且不会自动修改，兼容明确需要共享日志的服务组。

doctor 会分别验证当前 CLI 与守护服务定义中的 Node.js。对于服务保存的 `nodePath`，检查会实际执行 `--version`，因此路径虽然存在但不可执行、不是 Node，或版本低于 24 时都会产生 `service-node` 错误；用户级服务可通过 `--fix` 改用当前 doctor 的 Node 并重新生成定义，系统级服务则需要以管理员权限重新安装。

服务入口也不再以 `binPath` 存在作为充分证据。doctor 会解析符号链接后的真实文件，查找其所属 `package.json`，并确认包名是 `onebots`、版本与当前 CLI 一致且入口正是 manifest 声明的 `bin.onebots`。因此停止状态下仍能发现服务引用旧版安装、替代脚本或损坏清单；用户级 `--fix` 会改用当前 CLI 入口。

systemd unit、launchd plist 等平台服务定义无法读取或比对时不会再让 doctor 中断；`service-definition` 会以不包含文件内容的路径诊断令门禁失败。POSIX 上的 `service-definition-mode` 允许 unit/plist 公开读取，但拒绝组或其他用户写入；用户级 `--fix` 可恢复 `0644`，系统级只报告风险。安装器会原子替换定义并主动恢复 `0644`，因此重新安装也能消除既有危险权限。用户级 `--fix` 写入定义后会再次读取并与新元数据比较，只有结果一致才标记为 `fixed`。若 systemctl、launchctl 或任务计划程序在修复期间失败，doctor 仍会返回完整报告，保留修复前的 Node 与入口证据，并以定义路径报告失败，不回显底层命令可能携带的环境或文件内容。

Windows 用户级服务会同时验证任务计划 XML 与实际执行的 `onebots-user-runner.mjs`，包括 Node、CLI 入口、配置、插件选择、工作目录和日志输出。任务计划直接用 Node 执行 runner，不经过 `cmd.exe` 或 PowerShell；runner 以数组恢复完整参数，因此路径或配置值中的空格、`&`、`%VAR%` 和引号不会被 shell 解释。任一文件缺失或被修改都会让 `service-definition` 失败；重新安装或用户级 `doctor --fix` 会原子重建两份文件并清理旧 `.cmd` runner，再以同一渲染契约复验。卸载会移除任务 XML 与新旧 runner，但保留日志和用户数据。

Windows 系统级服务通过状态目录中的 `onebots-system-runner.mjs` 以数组无损传递完整参数，避开 `node-windows` 按空格拆分 `scriptOptions` 导致配置或入口路径失真的问题。WinSW XML 与 `.exe` 仍安装在 CLI 入口旁的 `daemon/` 目录；doctor 会同时验证 runner、Node、wrapper、工作目录、日志目录和重启策略。启动、停止与状态查询使用 WinSW 实际注册的 `onebotsgateway.exe` 服务 ID。任一文件或启动契约漂移都会失败并要求管理员重新执行 `onebots install --system`；卸载时会一并清理 runner。

服务安装本身也是事务。OneBots 先写入并注册候选平台定义，再按完整启动契约复验 unit、plist、任务 XML 或 WinSW 文件，最后才原子提交私有 `service.json` 元数据。平台命令、定义复验或元数据提交任一步失败时，已有安装会恢复上一份定义并再次复验；首次安装则撤销注册并清理候选定义与 runner，不留下无法由 CLI 管理的半安装服务。若恢复也失败，错误会同时保留原始安装问题与回滚证据，避免把受损旧服务误报为已恢复。

`service-permissions` 会验证保存服务元数据与日志的状态路径确实是当前进程可遍历、读取和写入的目录。普通文件占位、目录缺失或访问权限不足都会以只包含目标路径的错误令部署门禁失败，不会把原始文件系统异常带入报告。

`GET /api/adapters` 携带禁止缓存的应用、版本、实例和运行契约身份。Web 校验最小运行态结构后会独立展示和操作这份可信账号清单；只有把目录能力合并进同一视图时才要求两份身份完全一致。doctor 也会把账号清单与公开健康探针身份交叉验证。实例在页面加载后已经切换时，上线或下线请求携带的标准预期实例 header 或兼容 `expected_instance_id` 会由服务端以 HTTP 409 和 `ACCOUNT_INSTANCE_MISMATCH` 拒绝，旧客户端省略两者时仍保持兼容。反向代理因此不能把一个实例的账号快照与另一个实例的能力或操作入口拼成可信管理状态，而独立能力目录故障也不会隐藏真实账号。

账号管理摘要还会为每个协议出口返回 `name`、`version`、`path` 和 `lifecycleStatus`。机器人管理页会分别显示等待启动、启动中、就绪、停止中、已停止或失败，不再用账号 online 状态掩盖某个协议出口的启动失败。`GET /api/adapters` 的 `accountLifecycleControl` 会分别声明适配器是否真实实现手动上线和下线；Web 只为已实现的方向开放按钮，其他账号明确显示“不支持手动切换”。`POST /api/bots/start` 与 `/api/bots/stop` 会校验请求身份：缺字段返回 HTTP 400，适配器或账号不存在返回 404，插件未实现该操作返回 501。Web 把账号运行态快照的实例号同时放入标准预期实例 header 与兼容 JSON 字段，禁止缓存和重定向；服务端在读取正文和调用适配器前拒绝已切换实例的旧页面，并让成功与失败响应都通过标准 header 和正文声明处理实例。Web 只有在响应头与完整快照身份一致、正文再次闭合应用、实例和目标账号后才报告成功；空 HTTP 200、跨实例响应或其他账号的回执都不能证明切换完成。旧管理 WebSocket 的 `bot.start` / `bot.stop` 复用完全相同的执行与错误分类并继续支持兼容 JSON 实例字段：成功仍返回兼容的 `bot.change`，失败则返回可用 `echo` 关联的 `bot.change.result`，并携带稳定错误码；畸形 JSON 和插件异常不会再成为无回执的消息监听器拒绝。HTTP 与 WebSocket 还共享同一份按账号互斥状态：任一客户端正在切换某账号时，其他上线或下线请求返回 HTTP 409 或 `ACCOUNT_LIFECYCLE_CONFLICT`，不会让两个插件操作交错。手动切换、账号配置事务与完整重载通过 `@onebots/core` 的 `acquireRuntimeOperation()` 取得同一运行态租约，因此操作期间 `/ready` 会撤销就绪并声明 `reloading: true`，其他冲突操作不会开始。租约把布尔锁与操作原因作为一个原子边界发布，`release()` 幂等且用私有所有权令牌阻止过期释放清掉后续操作；调用点取得租约后立即进入 `try/finally`，所以读取旧配置等同步前置步骤失败也会恢复 readiness。`runtime_operation` 会进一步区分 `configuration_reload`、`account_configuration`、`account_lifecycle`、`idle` 与无法由嵌入式宿主证明原因的 `unknown`，doctor 和 Web 因此能准确显示“完整配置重载”“账号配置事务”或“账号上下线切换”，不会把所有短暂不可用都误报为配置重载。`onebots_runtime_operation{operation="..."}` 为每种状态持续输出互斥的 0/1 指标，原有 `reloading` 字段和 `onebots_reloading` 指标继续兼容。不同账号仍可并行操作，最后一个操作完成后才恢复 readiness；失败路径同样释放租约。Web 会直接显示服务端的限长单行诊断，非 JSON 响应则带 HTTP 状态安全回退，不再把所有原因压成“操作失败”。doctor 在验证合法管理凭据后会读取同一份受保护的运行态，直接报告 `平台.账号/协议.版本`；独立的 `management-capabilities` 检查会逐个验证适配器默认清单、账号级覆写和 `accountCapabilityErrors` 的闭合契约。仅声明 `capabilityDeclared` 却缺少有效清单、覆写不对应已配置账号、清单结构畸形、同一账号同时发布覆写与不可用诊断，或任一账号能力证据不可用，都会产生 `error`，使普通与 `--strict` 门禁失败，同时不掩盖账号和协议生命周期的独立结论。零账号时则明确报告已验证的适配器默认清单和“尚未配置账号”，不会用“0 个账号均可信”代替实际证据。公开的 `/ready` 仍只返回平台级聚合，不暴露账号标识。

同一次在线诊断还会验证管理面安全边界：匿名请求必须从 `/api/auth/me` 得到 HTTP 401，匿名根 WebSocket 必须在升级前得到 HTTP 401；随后使用配置中的 `access_token`（也支持 `ONEBOTS_ACCESS_TOKEN`）或用户名密码确认合法 HTTP 请求和 WebSocket 握手仍然可用。匿名 HTTP/WebSocket 会并行执行；取得凭据后，合法 HTTP、在线配置、运行态、账号能力与 WebSocket 探针也会并行执行，同时保持稳定的报告顺序。每项仍有独立的 2 秒边界，慢代理不会把所有超时串行累加。用户名密码探测生成的临时会话会在全部认证探针结束后注销。若自定义宿主只在内存中提供凭据、doctor 无法从配置或环境取得，匿名拒绝仍会验证，两项合法凭据探测则标为警告。

doctor 还会实际加载服务选用的插件，并使用它们注册的 Schema 校验完整账号和协议配置。每项成功结果会包含实际解析到的包名与版本，`plugin-selection` 检查会逐类别记录插件来自 CLI、配置文件还是服务定义，并给出模块解析目录。没有 `plugins` 的旧配置仍应传入与启动命令相同的 `-r` / `-p` 参数。

默认诊断已安装服务时，服务定义继续是实际运行契约。显式传入与服务定义不同的 `-c` 则表示验证一份独立候选配置：doctor 使用候选文件自己的插件默认值，不会把旧服务的插件混入结果，也不会因路径不同判定服务定义失效；即使同时传入 `--fix`，也不会改写那份无关的服务定义。这使发布流水线可以在切换服务前可靠验证下一版配置。

受保护的 `GET /api/system` 在 `plugins` 字段返回当前进程已通过入口加载和注册契约校验的适配器、协议及其包名、版本、真实入口路径；Web 管理端的「系统信息 → 运行时插件」展示同一清单。该响应携带禁止缓存的应用、版本、实例和运行契约身份，正文重复声明同一身份。Web 会先验证配置状态、插件条目和正文身份，再与 `/health` 交叉核对；不一致时隐藏系统快照并禁用备份与重启入口。doctor 也只会把同一公开实例的 `configState` 纳入部署结论。该信息来自正在运行的进程，可用于确认更新后是否已经重启到预期版本，也能区分同名插件实际来自哪个安装位置。管理 WebSocket 的初始 `system.sync` 同步相同数据。

「备份到仓库」会把当前系统快照的 `instance_id` 同时放入标准预期实例 header 和兼容 JSON 字段。服务端在读取配置和调用远端备份前拒绝已被其他实例接管的请求，并让成功与失败响应都通过标准 header 和正文声明应用、版本、实例与运行契约。Web 只有在响应头与系统快照身份完全一致、正文再次闭合应用与实例后才报告成功；重定向、代理跨实例拼接和仅伪造正文的响应都不能成为备份成功证据。旧客户端仍可省略实例字段。

受保护的 `GET /api/config` 与 `/api/config/schema` 携带同一份不可缓存应用、版本、实例和运行契约身份；配置正文还携带基于精确字节生成的 `sha256` 修订号。Web 配置页并行读取两者，只有身份一致、修订号有效、Schema 与 YAML 都可解析时才原子开放表单、下载和写操作。保存完整配置以及新增、编辑、删除账号时，页面同时发送实例和配置修订号前置条件；服务端在写盘、构造适配器或切换账号前以 HTTP 409 拒绝服务已经重启或配置已被另一管理操作更新的旧页面。保存成功回执还必须证明处理实例并返回新的修订号。旧客户端可以省略两项前置条件，但仍会收到新增的证据字段。

账号删除的正式管理契约是 `POST /api/remove`，目标平台、账号和可选的 `force` 布尔值放在 JSON 请求体中。Web 管理端只使用该入口，浏览器预取、链接扫描或中间缓存不会再把读取动作误解为删除请求。旧版客户端使用的查询参数 `GET /api/remove` 暂时保留兼容，并返回带弃用日期的 `Deprecation` 与迁移 `Warning`；新集成应迁移到 POST，两种入口都继续执行相同的实例和配置修订号前置条件。

setup、Web 管理端与运行时账号操作通过同一原子写入边界保存配置：新内容先在配置目录完成写入与同步，再替换正式文件，避免进程退出留下半截 YAML。Web 保存随后立即热重载账号与协议；应用失败会恢复磁盘和运行态的上一版本，宿主参数变更则返回需要重启的字段。单账号新增、编辑与删除也会同时锁住其他配置变更并撤销 readiness；只有账号启动或停止与配置落盘全部成功才会提交。新增和编辑会先把候选账号放入当前完整配置，复用启动时相同的适配器、协议及继承配置 Schema；缺少身份、平台凭据、已加载协议出口或字段类型错误会在构造适配器前以 HTTP 400 拒绝。平台登录、协议启动或写盘失败时，候选账号会被清理，旧账号、内存配置和磁盘文件会一起恢复；恢复本身失败时，响应会聚合原始错误与回滚证据。重复新增已有账号会被拒绝，配置事务冲突由管理 API 返回 HTTP 409，客户端可在当前操作结束后重试。更新已有配置时会把紧邻的上一版本保存在 `<config>.bak`；新配置默认权限为 `0600`，已有配置继续沿用原权限。setup 或启动入口如果需要生成并持久化新的管理鉴权码，会把正式文件和本次备份同时收紧为 `0600`，不会让新凭据继承原文件的组读或公开权限；使用环境 Secret 而不落盘凭据时仍保留部署者有意设置的共享模式。恢复前仍应先用 `onebots doctor` 校验备份内容。

POSIX 部署中，doctor 的 `config-dir-mode` 还会验证配置文件实际所在目录不允许组或其他用户写入。文件本身即使是 `0600`，可写父目录仍允许其他用户通过重命名替换同一路径，因此无 sticky bit 保护时会直接使部署门禁失败。配置路径自身或任一祖先目录为符号链接时，检查会遍历完整入口链；任一链接所在目录可被替换时，`config-entry-dir-mode` 会发布聚合风险，安全的目标文件和目标目录不会掩盖可篡改的入口。安全的系统路径链接不会增加无操作价值的成功项。`0755` 等仅允许遍历和读取目录项的常见项目目录可以通过；`1777` 等启用 sticky bit 的共享临时目录保留为警告，严格模式仍会拒绝。doctor 不会自动修改可能由其他应用共享的父目录，需由目录所有者明确调整权限或把配置迁入隔离目录。

Web 扩展安装还会记录包管理器执行前的插件版本。即使 npm/pnpm 在改写包后因生命周期脚本、网络或超时非零退出，只要已安装版本、依赖声明、公开锁文件或包管理器内部锁文件任一证据已经变化，OneBots 就会先反向恢复；包管理器成功后若落盘版本校验、隔离预检或配置提交失败，也进入同一恢复边界：原来没有该插件时移除新增包，原来已有其他版本时精确装回，并再次读取包清单、依赖声明与锁文件摘要确认结果。恢复后元数据仍有漂移也会判定为恢复失败，不会被掩盖，扩展中心的失败记录会同时保留原始安装错误和恢复错误，便于人工修复依赖与锁文件。

同一运行目录的 Web 扩展安装和 `onebots update` 会取得同一份 `.onebots-package-mutation.lock` 跨进程租约。多个受管实例、反向代理重试、并行管理请求或 CLI 更新因此不能交错修改 `package.json`、锁文件和 `node_modules`，也不能用各自的旧快照回滚另一个操作的成功结果；后到操作会带出当前事务、主机、进程号、操作 ID 与开始时间，Web 请求对应返回 HTTP 409。受保护的 `GET /api/extensions/package-mutation` 会主动返回 `idle`、`active`、`recoverable` 或 `invalid` 状态以及经过脱敏的所有者证据，绝不返回租约 token。扩展目录与租约响应都携带禁止缓存的应用、版本、实例和运行契约身份；扩展目录还携带从其实际解析内容生成的配置修订号。扩展页只有在两份身份完全一致、修订号有效时才采用可执行快照，并把实例与修订同时作为安装请求的前置条件；服务端在读取配置或调用包管理器前以 HTTP 409 拒绝已重启实例或被其他管理操作改写配置的旧页面。安装成功回执必须通过标准响应头与正文证明处理实例，并返回配置提交后的新修订号，Web 验证完整回执后才会进入重启流程；doctor 的 `management-extensions` 检查也把修订号列为在线扩展证据的必需字段。机器人页还会把目录身份与能力目录身份交叉验证，避免反向代理把不同实例的快照拼成可操作状态。扩展页在采用目录与租约响应前还会校验唯一扩展身份、安装/加载/版本闭合、配置目标、安全 HTTPS 引导链接、能力清单与派生摘要，以及租约状态与所有者的对应关系；两份响应全部通过后才会原子替换当前视图。畸形响应不会让机器人页误判协议已加载，也不会用新目录配合旧租约开放安装。扩展页面会持续观察活跃的跨进程安装或更新，在事务结束前展示所有者并禁用安装；可回收的遗留租约则明确说明会由下一次包变更安全回收。

更新命令的确认提示不会把确认前读取的状态当成写事务基线。取得上述租约后，更新器会重新读取持久化插件选择、每个目标包的实际版本、项目根和依赖元数据；插件选择已经变化时会在任何包管理器写入前要求重新运行命令，包版本已经变化时则以租约内的新版本作为失败恢复目标。如果另一项扩展安装在用户确认期间刚好完成，后续更新失败不会把它恢复成更早的版本或移除。

更新的安装命令及反向恢复各有 10 分钟上限，更新后隔离预检有 60 秒上限，避免包变更事务无限占用租约。租约所有权用随机 token 验证，过期持有者不能删除后来操作的租约。同一主机只有确认 PID 已退出才自动回收，不能因等待重启确认超过 30 分钟就抢占仍活跃的更新；不同主机或 PID 命名空间不能用本地进程探测冒充退出证据，远端租约超过 30 分钟后才可回收。损坏且仍在保护期内的租约不会被猜测删除，诊断会要求等待或人工检查运行目录。

扩展清单把当前 OneBots 目录验证版本、磁盘已安装版本与当前进程实际加载版本作为三份独立证据发布。安装或升级完成但尚未重启时，Web 不会因 loaded 为 true 就把新磁盘版本误报为已经生效；卡片会同时显示“已安装”和“当前进程”版本，把状态标为“等待版本切换”，并提供受管重启入口。前台进程无法自动拉起时则明确要求手动重启。适配器能力仍绑定当前进程实际加载的插件版本，协议扩展即使没有能力清单也能看到同一版本差异；任一版本缺失时显示未知，不推断一致。

OneBots 在加载任何第三方插件前，会深复制并冻结扩展安装目录、配置入口与全部引导步骤；扩展中心、安装白名单、doctor 和能力报告只消费这份宿主快照。插件即使深导入并改写原始目录导出，也不能替换允许安装的包名、隐藏官方条目或注入引导链接。固定包版本与能力快照的返回对象也会冻结，避免调用方获得引用后改写同一进程后续安装和验证所依据的身份。

`onebots doctor` 获得管理凭据后还会并行读取受保护的 `/api/extensions` 与 `/api/extensions/package-mutation`，独立验证扩展证据契约、运行版本收敛和共享运行目录没有未完成的包变更。两份管理响应必须来自同一实例，并与公开健康和就绪探针确认的应用、版本、实例及运行契约一致；缺少身份或出现分裂快照会直接使检查失败。扩展目录必须与当前 OneBots 的官方闭集完全一致；每项的类型、名称、包名、配置目标、引导步骤和固定目标版本都要匹配随包快照，适配器能力清单必须结构有效、摘要可重新推导，未加载目录快照还必须逐项等于当前发布证据。活动安装、历史终态、`installing` 标志和时间顺序也要闭合，私有租约 token 不能混入响应。已启用扩展缺少磁盘依赖或没有加载、已加载版本缺失或不同于磁盘版本、已启用或已加载扩展的磁盘版本偏离当前 OneBots 验证版本、活跃或无法验证的跨进程租约、可回收但尚未清理的遗留租约、安装事务未结束，以及目录、配置或包清单诊断都会使该检查失败并给出具体扩展或事务证据；相同的全局目录错误只报告一次。没有管理凭据时该项为 warning，因此 `--strict` 仍会拒绝无法证明扩展版本和包变更静止状态的部署。公开 readiness 继续只表示当前进程能否服务，不会在一次已完成但等待重启的扩展升级中提前摘除流量。

扩展安装按运行目录及其最近项目根的锁文件、workspace 声明、依赖协议和 `packageManager` 选择 npm 或 pnpm。即使 OneBots 从 pnpm workspace 成员目录被 `node` 直接启动，也会识别上层 workspace；清单中出现 `catalog:` 依赖时也会直接作为 pnpm 证据，不会误用 npm 解析并在下载阶段才报 `EUNSUPPORTEDPROTOCOL`。`ONEBOTS_EXTENSION_ROOT` 或部署目录是符号链接时，包管理器证据会沿链接目标的规范化真实路径查找，安装命令仍在指定运行目录执行；因此链接到 workspace 成员不会因链接所在父目录缺少锁文件而错误回退 npm。独立 npm 项目仍优先采用自己更近的 `package-lock.json` 或发布部署常用的 `npm-shrinkwrap.json`；即使进程从 pnpm 环境启动，也不会因此改写成另一套锁文件。如果 npm 锁文件与 `catalog:` 依赖同时存在，OneBots 会把它视为冲突并在启动包管理器前要求删除残留锁文件或修正依赖声明。同一目录同时出现其他 npm 与 pnpm 证据，或声明 Yarn、Bun、无效 `packageManager` 时，也不再猜测或降级到 npm；扩展清单、安装端点、doctor 和 update 会给出目录级错误，要求只保留实际包管理器对应的锁文件和声明。

发布工作流会真实打包所有公开包，并读取 tarball 内最终生成的 `package.json`。除入口与生产文件边界外，门禁还会拒绝残留的 `catalog:`、`workspace:`、`file:`、`link:`、`portal:` 或 `patch:` 依赖协议，避免 workspace 源清单在发布转换失败后形成 npm 无法安装的制品。

调用包管理器前，扩展中心还会验证运行目录确实属于当前 OneBots：项目清单必须自身为 `onebots` 或明确声明该依赖，目录内安装的包名和版本必须与当前进程一致。运行根、已安装 OneBots、服务入口、更新目标与包管理器识别统一使用同一套 1 MiB 常规 manifest 文件边界，因此超大、越界或特殊 `package.json` 会在权限检查、命令执行、依赖写入或接受更新制品前失败。运行目录以及已有的 `node_modules` 也必须对当前进程可写；只读容器挂载或错误的目录属主会在启动包管理器前直接失败。OneBots 还会按该目录的锁文件、workspace 和 `packageManager` 选择 npm 或 pnpm，并证明对应入口存在于当前进程的 `PATH`；缺少 pnpm 时会提示安装或通过 corepack 激活。安装端点随后以 2 秒、64 KiB 的边界执行该确切入口的 `--version`，要求 npm >=7.0.0 或 pnpm >=9.12.0；旧版本、异常输出或服务账号无法执行都会在读取配置和下载依赖前失败。通过校验后，安装和失败恢复会继续使用同一绝对入口，不再按短命令名二次搜索 PATH 或因项目证据变化切换包管理器。全局 CLI 从无关项目启动、`ONEBOTS_EXTENSION_ROOT` 指错目录、依赖尚未安装或旧版本 CLI 管理新目录时都会在读取配置和修改依赖前失败，并给出应切换目录或从目标目录启动的诊断。扩展清单 API 会提前发布路径可用性错误，Web 只会禁用确实需要修改依赖的卡片；已安装且版本匹配的扩展仍可直接启用和预检。服务端安装端点会在读取配置和下载依赖前重新校验，不能靠旧页面绕过。`onebots doctor` 的 `extension-root` 与 `package-manager` 检查复用相同判断，额外记录实际包管理器版本，并把结果写入文本和 JSON 报告；显式的 `ONEBOTS_EXTENSION_ROOT` 优先，否则使用守护服务或当前诊断的插件解析目录，因此错误、不可写、缺少包管理器或版本过旧的安装目标会直接使部署门禁失败。版本命令失败时不会回显其 stdout/stderr，避免注册表凭据进入诊断。若 `config.yaml` 损坏或不可读，扩展清单会降级为未启用状态并发布脱敏的 `runtimeConfigError`，版本化平台能力仍可浏览；Web 会显示原因并禁用安装，服务端也会在下载依赖前以 HTTP 422 重新拒绝写操作。

Web「系统信息」、扩展安装流程和管理终端的重启请求共用同一安全边界：先执行服务工作目录中的插件与配置预检，响应返回后调用 `app.stop()`，让账号、协议、WebSocket 与 HTTP 资源按生命周期顺序释放，再以守护进程可识别的失败码退出。优雅停机超过 30 秒会记录错误并交由守护进程强制切换，避免重启永久挂起。系统页和扩展页必须先通过禁止重定向的 `/health` 取得当前 OneBots 的应用、版本、`instance_id` 与可选运行契约，再通过标准预期实例 header 和兼容 JSON 字段把身份随重启请求发回；服务端在预检和调度前拒绝已被其他实例接管的过期请求。成功、拒绝与预检失败响应都发布标准实例 header 和正文身份，成功正文还声明调度状态；Web 要求响应头与重启前身份完全一致，并再次校验正文后，才会等待不同的新实例。旧客户端可以继续省略请求身份，但仍会收到包含当前实例的结构化回执。每次 `/health` 与 `/ready` 探针都有独立的 2 秒超时，代理保持连接却不返回内容时也会留下明确证据并继续有限重试。仅有 HTTP 200、旧实例仍在线、空回执、跨实例响应或身份字段缺失都不会被当作重启完成。

每个应用会在构造时固化自己的配置目录、配置文件、数据目录与日志文件路径。嵌入式宿主或同一测试进程随后创建另一个 `App` 并切换 `BaseApp.configDir` / `configFileName` 兼容默认值时，已有实例的账号事务、配置保存与热重载、管理端读取、数据库、安全审计、日志观察和 Hugging Face 备份仍使用原实例路径，不会跨实例读写。静态字段继续用于创建实例前设置默认路径；运行中的代码应使用实例公开的 `configDir`、`configPath`、`dataDir` 与 `logFile`。

获得管理凭据后，`onebots doctor` 还会把本次命令指定的配置文件和派生数据目录，与同一在线实例从受保护 `/api/system` 返回的 `configPath`、`configDir`、`dataDir` 逐项核对。路径字段必须是绝对路径，配置目录必须与配置文件父目录闭合；缺失、内部矛盾或指向另一份 `-c` 配置都会使 `management-config` 检查失败。`configState: in_sync` 因此只能证明当前诊断目标对应的在线实例，而不能让同端口上使用另一份配置的 OneBots 进程通过生产门禁。

进程会在启动、每次成功热重载及账号配置落盘后保留配置文件的不可逆摘要。受保护的 `GET /api/system` 通过 `configState` 字段与 Web「系统信息 → 配置状态」只公开 `in_sync`、`drifted` 或 `unavailable` 及最近应用时间，不公开摘要或配置内容。若配置被外部编辑、挂载替换，或者 Web 保存的宿主字段仍等待重启，状态会保持 `drifted`；成功重新加载或重启后才恢复 `in_sync`。同一状态会投影到公开 `/ready`，不同步时返回 HTTP 503。`onebots_ready` 直接发布与该端点相同的最终判定，告警规则无需重新组合账号、协议、配置和运行态操作条件；`onebots_config_status{status="..."}` 用互斥的 `in_sync`、`drifted`、`unavailable`、`untracked` 序列保留具体原因。兼容指标 `onebots_config_in_sync` 在不同步时仍为 `0`，嵌入式宿主未跟踪配置时仍为 `1`；需要区分这两种情况时应使用 `onebots_config_status`。doctor 会把漂移和文件不可读分别报告为可操作原因。管理 WebSocket 的初始 `system.sync` 也携带同一状态。

在 POSIX 系统上，doctor 会分别检查正式配置与 `.bak` 的权限。`0600` 视为私有；`0640` 等仅允许同组读取的模式会给出警告但不自动修改，以兼容服务账号共享；其他用户可访问或同组用户可修改会使检查失败。显式使用 `--fix` 时，这类高风险权限会收紧为 `0600`，JSON 报告中的 `fixed` 字段可供部署脚本留痕。

doctor 还会验证配置文件同级的 `data` 路径确实是当前进程可读取、写入和遍历的目录。默认数据库、安全审计和管理终端日志都使用该目录；守护服务与前台模式不会再按各自的当前工作目录分散日志缓存。若 `database` 使用绝对路径或通过相对路径离开默认目录，doctor 会继续验证解析后的实际数据库文件及其父目录，确保 SQLite 能创建 journal/WAL 文件；空路径、目录占位、不可读写文件或不可创建父路径都会使门禁失败。POSIX 上的 `database-mode` 与 `database-dir-mode` 还会分别证明数据库文件未向其他用户开放、实际父目录不允许替换数据库路径；带 sticky bit 的共享临时目录保留为严格模式可见的警告。doctor 不会自动修改用户指定的数据库存储，需由文件或目录所有者处理。普通文件占位、错误的卷挂载或权限不足也会直接使默认数据目录检查失败，避免运行时存储初始化后置报错；数据目录缺失时默认给出警告，只有显式使用 `--fix` 才会创建并再次验证目录，既有冲突路径不会被替换。

新建数据目录在 POSIX 系统上使用 `0700`。SQLite 运行时也会以 `0700` 创建缺失的自定义父目录，并在打开前把新旧数据库文件收紧为 `0600`，避免 Node 默认 umask 产生可公开读取的 `0644` 文件。doctor 的 `data-dir-mode` 检查会把其他用户可访问或同组用户可修改的权限判为错误，`--fix` 可明确收紧为 `0700`；仅允许同组读取或遍历时保留警告且不会自动改变，以兼容有意采用服务组共享的部署。单个数据库或日志文件的权限不能抵御可写目录中的路径替换，因此该检查与配置文件的 `config-mode`、备份权限检查相互独立。

启用 `public_static_dir` 时，相对路径的实际目录也必须留在配置目录内；通过符号链接跳转到外部目录会被拒绝。管理端上传先在静态根内写入唯一临时文件，再原子替换最终文件；已有符号链接、目录或其他非常规文件不会被跟随或覆盖，删除接口也只管理常规文件。即使静态根尚未配置或请求前置条件失败，已经由上传中间件创建的临时文件也会被清理。需要使用配置目录外的静态目录时，应明确配置绝对路径并单独控制其所有权和写权限。

受保护的静态文件列表在标准响应头和正文中发布应用、版本、实例身份，以及绑定解析后静态根和全部目录项身份的 SHA-256 修订号。Web 只有在响应头、正文和修订闭合后才开放上传与删除，并把实例和静态目录修订同时作为写请求的前置条件。同一实例内如果文件被其他页面、自动化或外部进程新增、替换、删除，或配置切换到另一静态根，服务端会在触碰目标前以 HTTP 409 拒绝旧页面。成功回执还必须由同一实例签发，并同时在响应头和正文返回变更后的新修订；Web 验证后才报告完成并刷新列表。旧客户端可以省略前置条件，但仍会收到这些证据字段。

doctor 的 `public-static-dir` 检查复用运行时的真实路径规则，并在 JSON `target.publicStaticDirectory` 中公开最终目录。未创建的目录是警告，`--fix` 可安全创建；越界、路径类型错误或无法读取会直接失败。目录可读取但当前进程不可写时保留警告，明确表示静态托管可用而管理端上传不可用。

`onebots setup` 与前台启动复用同一数据目录边界。首次初始化或 `setup --force` 会先验证或创建数据目录，再写入、备份配置；若挂载目标冲突或权限不足，命令会保留原配置、既有备份和冲突路径，避免显示失败后却留下已经生效的半套配置。非交互环境遇到已有配置时仍不会覆盖或创建备份，但会先验证 YAML、基础 Schema、适配器与协议配置及所选插件；若复用文件内持久化管理凭据，还会验证配置、既有备份和父目录的 POSIX 权限，再验证或创建同级 `data` 目录。高风险权限会在产生数据目录前失败并保留全部文件，组只读权限则以安全提示保留；只有现有配置具备实际启动条件才成功退出。直接启动缺少配置的目录时也会先通过这项验证，再生成默认配置与鉴权码。

“已加载”要求插件入口完成初始化，并注册 CLI 名称对应的工厂与配置 Schema。可导入但漏注册、名称不匹配或仅注册工厂而缺少 Schema 的插件会被 doctor 和所有服务预检判为错误，而不会延迟到启动后或 Web 管理端才暴露。

插件包身份也必须形成连续证据：候选目录中的 `package.json#name` 必须与实际请求的 npm 包名一致，固定版本校验和注册契约才会继续执行。OneBots 会在读取前确认 manifest 位于实际包根、是常规文件且不超过 1 MiB，并要求最终入口也是实际包根内的常规文件；目录、设备等特殊文件不能冒充清单或代码入口。整个包目录仍可由 workspace 或 pnpm 软链接提供，但包内 `exports`、`module` 或 `main` 指向的入口不能通过二次软链接逃到实际包根之外。非常规或越界入口会在任何插件代码执行前被拒绝。目录被错误复制、替换或损坏时，入口代码同样不会运行；即使 manifest 版本正确，扩展中心也会把该依赖标记为“无法验证”并显示具体原因，“修复”操作会要求 npm 或 pnpm 强制重新落下当前 OneBots 目录锁定的精确版本。包管理器即使成功退出，若落盘包仍无法验证，安装会失败并恢复安装前的依赖声明与版本。

Adapter 与 Protocol 注册表会在 Schema 首次注册时复制并递归冻结其对象、数组与正则表达式容器。插件随后改写原始对象，或通过 `getSchema()` / `getAllSchemas()` 尝试原地修改其他扩展的契约，都不会改变宿主实际使用的 Schema；同一原对象的重复注册仍保持幂等。数组和对象形式的默认值在每次配置校验时重新复制，因此不可变注册契约不会把冻结容器泄漏进账号运行配置。

适配器与协议的展示元数据也以冻结快照保存，`getMetadata()` 和 `getAllMetadata()` 不再暴露可改写的注册表内部对象。协议新增或移除版本时使用 copy-on-write 生成新的冻结版本列表，因此一个插件无法在加载事务结束后伪造其他插件的名称、来源信息或协议版本证据。

注册成功也不会让宿主盲目信任工厂返回值。适配器实例必须保留注册的平台身份和当前 App 引用，并提供账号创建、能力描述与生命周期方法；`createAccount` 返回值必须属于当前适配器，实例与配置都要保留请求的平台和账号 ID，并提供协议集合、生命周期、事件与分发接口；协议集合必须与账号配置中已注册的协议一一对应，不能遗漏、重复或注入未注册实例；每个协议实例还必须匹配注册的名称和版本、当前适配器与账号、配置中的协议身份，并实现完整运行接口。任一项不一致都会在实例进入账号或开始监听前抛出带扩展身份的验证错误。若账号在构造期已经注册 HTTP 或 WebSocket 路由，验收失败会同时关闭其路由作用域，避免错误插件随后以路径占用、readiness 异常或事件分发失败的形式暴露。

每次插件入口导入还会进入独立的异步注册时段。入口中的顶层 `await` 和导入完成前执行的异步任务仍属于本次事务，会统一接受注册归属检查与失败回滚。单个入口若在 15 秒内没有完成异步求值，前台启动、doctor 与服务预检都会报告具体插件的超时失败，立即关闭并回滚该注册事务，再允许后续插件继续加载；不会因一个永不返回的顶层 `await` 永久占住全局注册队列。入口创建的定时器或 Promise 若在事务验收结束或超时后才尝试注册、注销、清空或恢复 Adapter / Protocol 注册表，则会收到“插件注册事务已结束”错误，不能把迟到修改泄漏到已验证运行态。该时间边界针对能让出事件循环的异步初始化；插件入口仍不应执行同步死循环或长时间阻塞 Node 事件循环。

若入口已经成功求值，但随后因缺少 Schema、注册越界等契约问题被拒绝，OneBots 会让该入口在同一进程的下一次加载中重新执行，而不是复用 Node 的 ESM 成功缓存。这样修复或重新安装插件后可以直接重试；一旦某次事务通过验收，后续重复加载仍复用同一模块实例并保持幂等。

插件通过验收后，当前进程会把其逻辑名称锁定到实际包名、manifest 版本和规范化入口路径。相同身份的重复加载保持幂等；同一逻辑名称随后解析到另一包、另一入口或磁盘上的另一版本时，会在执行入口前拒绝，不允许冲突包先产生注册表之外的副作用。加载清单继续发布进程中实际求值的版本，不会把 ESM 缓存中的旧代码误标成刚落盘的新版本；依赖升级后应重启 OneBots 以建立新的插件身份。

`onebots mcp` 的 stdio 入口也复用当前进程已经验收的 `@onebots/protocol-mcp-v1` 规范化入口，不会从 `onebots` 包自身重新解析一份协议。这避免 pnpm 严格依赖布局中网关已成功加载同级插件、stdio 命令却误报未安装。stdio 请求按输入顺序执行；异步处理失败时，只对带 `id` 的请求返回 JSON-RPC `-32603`，通知不产生响应，错误详情进入正常日志而不会写入 stdout。账号选择、MCP 配置、入口导入或导出校验若在 App 启动后失败，命令会完整停止已创建的账号、协议与监听器；清理也失败时同时保留两份错误。stdin 关闭会等待已接收请求完成，重复关闭只复用同一次停止操作。

适配器实例创建时会把注册元数据中的默认能力清单与 `describeCapabilities()` 的默认结果逐项比对，并提前确认每个标为支持的动作都有具体实现。清单不一致或动作仍落到基类占位实现都会阻止启动，避免扩展中心的选型证据与账号运行态能力相互矛盾；未声明注册能力的第三方适配器仍按“能力未知”处理，不会伪造结论。

账号构造同样使用明确的候选边界。Core 会在调用第三方 `createAccount()` 前记录 Adapter 账号 Map 的引用与有序条目；工厂只能返回候选实例，不能提前发布账号、删除或重排已有账号，也不能替换整个集合。无论工厂正常返回还是抛错，只要同步构造期间越过该边界，Core 都会恢复原集合并拒绝候选；恢复本身失败时同时保留边界错误与恢复错误。这避免首次启动、热重载和账号配置事务被未验收的幽灵账号污染。

Adapter 与 Protocol 的实例工厂也不能修改全局扩展注册表。Core 会在每次工厂调用前后比较 Adapter、Protocol、元数据和 Schema 的完整注册快照；注册、删除或清空等副作用会被恢复并使候选实例验收失败，工厂本身抛出的错误会作为原因保留。扩展注册应只发生在插件加载事务中，实例工厂只负责创建候选运行对象，因此一个账号配置不能悄悄改变后续账号可用的扩展集合。

Adapter 工厂构造期间注册的 HTTP 与 WebSocket 路由也有独立所有权。候选未通过身份、宿主、能力或动作实现契约时，这些路由立即撤销；验收成功后，作用域会一直归属于该 Adapter，并在完整停止、热重载、创建后钩子失败或新建账号回滚且不再需要该 Adapter 时关闭。冲突诊断会区分“适配器全局路由”和具体账号路由，避免无效或旧实例留下仍可访问的入口。

`GET /api/adapters` 与管理 WebSocket 会合并插件加载清单和账号运行态：适配器只要已经通过加载契约，即使尚未配置任何 Bot，也会返回注册名称、说明、插件版本和默认能力，并以空 `accounts` 明确表示“未配置账号”。机器人页因此可以直接比较已加载平台并进入账号配置，不会把零账号误判成“未安装适配器”。没有注册默认清单的第三方插件会返回 `capabilityDeclared: false`；Web 显示“能力未知”警告，空分类不能被解释为平台不支持，doctor 的 `management-capabilities` 也会失败并要求插件补充可信声明。

管理 API 发布账号能力前还会重新校验并复制冻结动态清单，再按结构内容与适配器默认清单比较。适配器即使为每个账号重新创建了内容相同的对象，也不会被误标为“账号专属清单”；真正不同的权限或订阅能力才进入 `accountCapabilities`。畸形清单和返回后被插件改写的对象不会成为 Web 能力证据。单个账号的动态清单读取或校验失败会记录适配器错误日志，并以 `accountCapabilityErrors` 返回长度受限的机器可读诊断，不会让整个 `/api/adapters` 或其他账号摘要失败；Web 会明确警告当前只是回退展示适配器默认清单，不能据此判断该账号的实际能力。

插件入口存在但初始化失败时，doctor 会保留底层首行错误，例如重复注册冲突或缺少运行时依赖，而不是只报告笼统的“初始化失败”。这类错误应先修复插件安装或命名冲突，再重新执行诊断。

使用 `onebots install -c config.yaml -r <adapter> -p <protocol>` 安装守护服务时，同一套插件加载与配置校验会在系统服务定义写入前执行。服务预检还要求配置文件自身包含 `access_token` 或完整的用户名密码；当前 shell 中临时设置的 `ONEBOTS_ACCESS_TOKEN` 不会被复制进 systemd、launchd 或 Windows 服务定义，因此不能作为守护服务的凭据证据。缺少持久化凭据时应将凭据写入配置，或先取消该环境变量，再执行 `onebots setup -c config.yaml --force` 安全生成并写入鉴权码。安装会在读取插件选择前记录配置的真实路径、设备、inode 和内容摘要，并在异步插件预检结束后复验；平台定义写入后、`service.json` 提交前还会执行同一检查。期间发生原子替换、内容改写或凭据权限放宽时，首次安装会清理候选定义，更新安装会恢复原定义，磁盘上的新配置保持不变并要求重新执行安装。安装、启动和重启还会复用 setup 与 doctor 的 POSIX 权限证据，重新检查配置、既有备份和父目录；公开可读、同组可写或可被其他用户替换的持久化凭据会在服务定义或进程状态改变前被拒绝。POSIX 服务安装还会在执行 systemd/launchd 命令和提交 `service.json` 前验证服务定义父目录不允许组或其他用户替换定义；原子写入前会再次检查，以覆盖取证与落盘之间的权限竞态。`onebots doctor` 的 `service-credentials` 和 `service-definition-dir-mode` 检查会发布同一结论，但不会回显凭据。仅暴露 `exports.import` 的插件、顶层 `await`、Schema 校验和初始化异常都按前台启动语义处理；预检失败不会留下一个必然无法启动的服务。首次安装不会立即启动；更新后的权威进程状态为停止时也会提示执行 `onebots start`。若定义实际变化且安装前后的进程状态都为运行，现有实例不会被暗中重启，命令会明确提示执行 `onebots restart` 以应用新定义；幂等安装相同定义则让实例继续运行。进程管理器状态无法确认或发生意外状态切换时会提示执行 `onebots status`，不会从旧快照推断当前状态。

`onebots start` 与 `onebots restart` 还会读取已保存的服务定义，以安装时的 `workingDirectory` 解析插件，并重新校验当前配置。这能捕获安装后被删除或损坏的插件与配置。两条命令也会复用状态报告的控制面权限证据：服务状态目录、`service.json`、systemd unit 或 launchd plist 及其父目录中的任一 error 级风险都会终止预检；warning 级的有意组共享仍保持可见但不阻断。隔离运行时预检与实例身份取证完成后，CLI 会在调用进程管理器前重复权限检查和平台定义一致性验证，并比较配置的真实路径、设备与 inode、内容摘要和持久化凭据权限；配置被原子替换、改写或放宽权限时必须重新运行命令。这关闭了长预检期间发生漂移的窗口。启动预检失败时不会请求操作系统启动服务，重启预检失败时也不会先停止现有实例。操作系统命令执行后，CLI 会在有限窗口内轮询 `/health` 与 `/ready`，要求在线应用名和版本与当前 CLI 一致、readiness 成功或处于可继续配置的首次部署状态，并要求两端声明同一个 `instance_id`。`start` 对已经在线的服务保持幂等；服务原本未运行但端口已被占用时，以及执行 `restart` 时，验证后的实例身份还必须不同于操作前。旧实例继续占用端口、两个探针分属不同实例、目标进程未上线或身份字段缺失时，命令返回失败并保留最后的探针证据，不会提前宣告启动成功。

启动与重启不会用当前 CLI 进程代替已保存的服务运行时。平台定义一致后，预检会实际执行 `nodePath --version`，确认版本至少为 24，再验证 `binPath` 属于与当前 CLI 同版本的 `onebots` 包且正是其 `bin.onebots` 声明；随后由该 Node 和入口在服务的 `workingDirectory` 中启动一次性子进程，加载保存的完整插件选择并校验配置。旧 Node、已删除或被替换的全局入口、相邻版本安装和只在当前 shell 中可解析的插件都会在进程管理器启动或停止任何实例前返回退出码 `2`，并给出可直接交给 `doctor` 或重新安装处理的原因。

CLI 启动与重启在调用进程管理器前也会复验平台定义与服务元数据一致。运行中管理页、扩展中心和终端发起的受管重启使用同一边界：当前进程必须以配置路径、Node、CLI 入口和工作目录匹配已安装元数据，且所有匹配 scope 的平台定义都必须有效，才会优雅退出交给监督器拉起。定义漂移时当前实例保持在线，并提示重新执行 `onebots install`，不会让一个健康旧进程退出后才暴露错误启动命令。

`onebots uninstall` 同样不会把进程管理器接受 stop 请求当作服务已经停止。它会在有限窗口内等待权威的停止状态，确认后才删除 systemd/launchd/Windows 定义和私有 `service.json`。若服务仍在运行、监督器重新拉起进程或状态查询不可用，卸载会失败并保留定义与元数据，仍可继续执行 `status`、查看日志或重试停止。平台删除命令和元数据提交也属于同一事务，不会忽略 systemd 或 Windows 任务删除错误；任一步失败都会重新写入并复验原定义，同时保留私有元数据。若恢复也失败，错误会同时保留删除与恢复证据并要求重新执行 `onebots install`。服务在恢复后仍保持停止，配置、日志和数据库在成功卸载后也保持不变。

`/health`、`/ready` 与 `/metrics` 都返回 `Cache-Control: no-store`，明确禁止浏览器和中间代理把瞬时运行状态当作可复用内容。doctor、status、启动/重启/更新验证以及终端仪表盘也以不可缓存请求读取探针；因此只要代理遵守 HTTP 缓存语义，部署门禁不会用旧实例的 `instance_id` 或旧 readiness 证明当前进程可用。终端仪表盘把 Web 页面 origin 与 Router HTTP 前缀分开处理：`o` 仍打开根页面，Health 则按规范化的 `path` 访问对应 `/health`。

`onebots ui` 终端运维面板中的启动、停止和重启键复用上述公开 CLI 命令边界。面板中的启动与重启同样先预检已保存的服务定义，并在操作后验证在线版本、readiness 与实例切换；失败原因会保留在面板中，而不会把底层进程管理器命令成功误报为服务可用。

`onebots stop` 会在发出停止命令后有限轮询进程管理器，只有服务不再处于运行状态才报告成功；超时会保留最后的状态证据。进程管理器查询失败不会再被当成 `running: false`：停止验证会继续重试，窗口结束仍无权威结果时明确报告“无法确认服务已停止”。`onebots start` 也会在当前状态未知时停止，不会向可能仍在运行的服务重复发出启动命令。Linux 使用对正常 inactive 仍成功的 `systemctl show ActiveState` 取证；macOS 只把 launchd 明确返回的“任务未加载”视为已停止，其他控制平面错误保持失败。macOS 上的停止操作会用 `launchctl bootout` 从对应 launchd 域移除任务，阻止 plist 中的失败自动拉起策略把刚停止的进程重新启动；后续 `start` 或 `restart` 会重新 `bootstrap` 服务定义。终端运维面板的停止键复用同一验证。

前台与守护服务进程收到 `SIGINT` 或 `SIGTERM` 时共用有界优雅停机协调器：同一轮信号只调用一次 `app.stop()`，并释放账号、协议、WebSocket 与 HTTP 资源。正常关闭会取消 30 秒兜底并以成功状态退出；若关闭抛错，错误会记录且兜底继续生效，残留 SDK 或网络句柄无法再让进程永久挂起。关闭一直未完成时也会在超时后记录 fatal 日志并强制退出，交还控制权给进程管理器。

核心停机编排会隔离扩展失败：一个协议停止失败不会阻止同账号的其他协议与账号监听器，一个账号失败不会阻止同适配器的其他账号，一个适配器或生命周期钩子失败也不会跳过其余适配器、数据库、WebSocket/HTTP、安全审计与 `close` 监听器。数据库、Router、HTTP 等生命周期资源的释放失败也会在其他资源完成清理后进入最终错误，而不会被 `cleanupError` 日志掩盖。所有阶段完成后才汇总错误交给进程信号层，因此既保留可诊断的失败退出状态，也尽量避免强制退出前遗留资源。

启动同样采用完整回滚边界。配置校验、管理路由与日志监听初始化、生命周期钩子或 HTTP 监听任一阶段失败时，OneBots 会释放已创建的账号、协议、数据库、Router、WebSocket/HTTP、文件监听及进程级日志拦截，并把该 App 实例标记为不可再次启动。若回滚步骤也失败，最终错误会同时保留原始启动错误与回滚错误；守护进程后续重试会创建全新进程和实例，避免在半初始化对象上重复注册路由或监听器。

安全审计写流同样属于可等待的停机资源。`app.stop()` 与启动失败回滚会等待已排队的审计记录刷新并关闭文件描述符后才返回；写入目录被卸载、删除或失去访问权限时，流错误会进入同一停机失败汇总，而不会在临时目录清理或进程退出后以未处理异常迟到。重复关闭保持幂等，不会再次操作已释放的流。

管理终端日志也属于可等待的停机资源。同一进程中的多个 App 实例共享一层 `stdout` / `stderr` 拦截，各实例只订阅自己的缓存与 SSE 客户端；任意实例停止时只移除自身订阅，最后一个实例停止后才恢复原始标准流。因此测试、嵌入式运行或切换实例即使不按创建顺序关闭，也不会把输出继续写入已关闭的缓存或形成重复拦截链。正常关闭还会先停止该实例的所有日志 SSE 心跳并结束客户端响应，再等待缓存写流彻底关闭后清空临时缓存，避免未完成写入在截断后重新出现。任一客户端或文件清理失败都在其他资源完成后进入停机错误；进程的同步 `exit` 监听只作为无法等待异步操作时的最后兜底。

`onebots status` 在读取配置或请求 HTTP 端点前，还会按平台复验 systemd unit、launchd plist 或 Windows task/service 的真实启动契约与 `service.json` 元数据一致。定义漂移或无法读取时直接返回“状态无法验证”，保留定义路径并停止 HTTP 取证，避免把一个受管进程与元数据地址上的无关 OneBots 实例拼成“已就绪”。JSON 报告的 `serviceDefinition` 会保存路径、`current` 一致性和脱敏错误。

状态报告还会实际执行服务定义保存的 `nodePath --version`，验证 `binPath` 是当前版本 `onebots` 包声明的 `bin.onebots` 入口，确认配置仍包含持久化管理凭据，并在 POSIX 系统上重新检查配置、既有备份和父目录的凭据权限。它还复用 doctor 的服务控制面规则，验证服务状态目录可安全访问、`service.json` 保持私有、systemd unit 或 launchd plist 不允许组或其他用户修改，且定义父目录不能替换该文件。JSON 中的 `serviceRuntime.valid` 汇总这些结论，`checks` 保留 `service-node`、`service-entry`、`service-credentials`、`config-mode`、`config-backup-mode`、`config-dir-mode`、符号链接配置按需出现的 `config-entry-dir-mode`、`service-permissions`、`service-metadata-mode`、`service-definition-mode` 与 `service-definition-dir-mode` 证据；文本模式也会逐项显示。任一配置路径或服务控制面权限检查为 error 时，状态命令不会再读取该路径提供的地址并执行 HTTP 探测，避免把可篡改目标的响应混入生产证据。凭据证据明确忽略当前 shell 的 `ONEBOTS_ACCESS_TOKEN`，因为该临时环境变量不会进入守护服务定义。该检查不依赖服务是否正在运行，因此停止状态可以直接解释下一次启动为何会失败；运行中的旧进程即使仍在响应，只要保存的 Node、入口、持久化凭据或任一高风险权限已失效，也会被标记为 `unavailable`，而不是继续宣告生产就绪。组只读的 `0640` 配置仍保留为警告且不单独破坏 ready 状态，方便有意使用服务组共享的部署归档这项例外。权限文件在取证过程中消失时会成为结构化错误，不会让状态命令崩溃。

服务启动后，`onebots status` 会同时显示进程管理器状态、`/health` 与 `/ready` 的语义结果，以及 Web 管理页在线检查，并打印独立的成对实例结论。管理页检查会请求 `target.webUrl`，要求返回受限大小的 HTML、与当前配置一致的 Router 前缀元数据，以及 `no-store` 和 `no-referrer` 响应头；通用 HTTP 200、错误前缀或缺失静态入口都会使状态不可用。输出会区分“运行中，已就绪”“运行中，待配置”“运行中，版本未验证”和“运行中，不可用”；在线主程序版本缺失或与当前 CLI 不一致、任一响应无法归属到具体 OneBots 实例、两个探针的应用版本或 `instance_id` 不同、服务已安装但未运行、任一探针失败时退出码为 `1`，服务未安装时为 `2`。首次未配置账号且两份身份一致时仍保持“待配置”并退出成功，便于继续使用管理面。CI/CD 可执行 `onebots status --json` 获取 `schemaVersion: 1` 的稳定报告；其中包含生成时间、当前 CLI 身份、服务 scope、配置路径、API 探测地址 `target.baseUrl`、Web 地址 `target.webUrl`、进程管理器证据，以及 `health`、`ready`、`probe-instance` 和 `management-page` 的分级结果与实例身份。顶层 `status` 使用 `uninstalled`、`stopped`、`ready`、`pending_configuration`、`version_unverified` 或 `unavailable`，`ok` 只在已就绪或允许继续首次配置时为 `true`。无法读取配置时，报告在 `probe.error` 中说明原因而不会伪造 HTTP 检查；服务元数据损坏时，`processManager.installed` 与 `running` 为 `null`，错误只公开元数据路径，且不会执行进程管理器命令或探针。进程管理器命令失败时，已安装证据仍保留，但 `running` 为 `null`、`processManager.error` 说明查询失败，顶层状态为 `unavailable`，doctor 同样把它作为错误而非“服务已停止”警告。这样轻量门禁既可直接使用退出码，也能归档并解析证据；需要完整配置和插件诊断时再使用 `onebots doctor --json --strict`。

`onebots update` 默认读取当前 `config.yaml` 的 `plugins` 选择，因此通过 Web 扩展中心后装的适配器和协议也会进入版本检查与更新；显式 `-r` / `-p` 仍可按类别覆盖配置，旧配置没有 `plugins` 时才回退到服务安装时的快照。更新器会先复用扩展安装与 doctor 的实际包管理器版本门禁，只有 npm >=7.0.0 或 pnpm >=9.12.0 的可执行入口才能进入 registry 查询、暂存下载、正式依赖写入和失败恢复；因此检查模式也不会把旧包管理器误报为可用于生产更新。更新器只查询目标 OneBots 主程序版本；主程序有新版本时，会先在临时目录以禁用安装脚本的方式暂存目标包，读取它随包发布的扩展版本目录并清理临时内容。所有所选适配器和协议都使用该目录中的精确版本，不会各自追随 npm `latest` 组成未经共同验证的运行环境；目录缺项、格式损坏或暂存失败会在修改正式运行目录前终止。对已安装服务，更新器还会在包管理器落盘前取得权威运行状态；控制平面不可用时不会修改软件包、锁文件或服务定义。包管理器成功退出后，更新器会从项目运行目录读取包清单；全局 CLI 场景则回退到当前 OneBots 安装根，逐个确认主程序与所有所选插件的实际版本等于上述验证版本。项目级 npm 更新只保存生产依赖并使用 `--omit=dev`，不会在生产运行目录恢复开发工具；从 pnpm 启动 npm 时还会移除 npm 不支持的 pnpm 专用环境配置，避免 `_icqqjs-registry`、`recursive`、`store-dir` 等警告污染诊断。npm/pnpm 在 Windows 上统一使用 `.cmd` 入口。包管理器非零退出时，更新器也会先比较操作前后的整组包版本、依赖声明及公开/内部锁文件摘要；若已经产生部分写入，就恢复全部原始版本，并复验包版本、依赖声明和锁文件摘要。任一包缺失或偏离都会报告完整期望/实际清单，并在服务预检、定义改写和重启前终止。落盘版本全部可信后，才会从服务的 `workingDirectory` 启动更新后的 CLI 子进程，以同一插件列表执行无连接预检。只有新运行环境成功加载全部插件并通过配置校验，才会改写服务定义并按确认结果重启。重启后，更新命令会在有限重试窗口内同时探测 `/health` 与 `/ready`：两份响应必须声明同一个 `onebots` 应用、目标版本和 `instance_id`，该实例还必须不同于重启前，且 readiness 成功或仍处于允许继续配置的首次部署状态，命令才会报告完成；代理把两次请求分发给不同实例时会继续重试，并在超时错误中保留双方身份。交互模式选择暂不重启时，更新命令明确提示磁盘依赖已更新但运行中的仍是旧实例。版本落盘校验或新运行环境预检失败时不会停止当前实例，也不会替换服务定义；更新器会在这个安全窗口内通过同一 npm/pnpm 恢复全部所选包的原始精确版本、移除原本不存在的包，并逐包验证恢复结果。若嵌入调用在依赖落盘后才发现状态查询失败，也会使用相同事务恢复依赖。恢复本身失败时，错误会同时保留原始问题与恢复证据，要求人工修复依赖和锁文件。服务定义改写或进程切换开始后的失败则保留新版本，不进行可能破坏在线实例的盲目回滚。

包管理器落盘前，项目更新目录必须自身为当前版本的 `onebots` 包，或明确依赖且实际安装同版本 OneBots，并通过与扩展中心相同的可写性检查；只依赖 `@onebots/core` 的 SDK 或插件项目不会被误判为网关运行目录。由另一版本的全局 CLI 进入项目时也会在修改依赖与锁文件前失败，并提示从该项目的 OneBots 安装执行更新。损坏的子目录清单可以由上层可信项目收敛；若整条路径都无法提供可信项目，更新会停止，不会悄悄降级为全局安装。

registry 查询、目标目录暂存、正式依赖写入和失败回滚始终执行同一个已验证的包管理器绝对入口；更新事务不会在这些阶段重新搜索 PATH 或切换包管理器。

registry 返回的主程序版本与目标目录中的每个插件版本还必须是精确 SemVer；标签、范围、前后空白或畸形版本会在启动暂存下载前失败。暂存包管理器的失败诊断会脱敏 registry URL 凭据、token 与 Bearer 值并限制长度，原始 stderr 不会作为异常 cause 继续传播。

主程序版本查询本身也有独立边界：它继续使用同一个已验证的包管理器绝对入口，并以受管服务或 `--packages-only` 的运行目录作为工作目录，使项目级 `.npmrc`、registry 与代理选择不依赖调用 CLI 时所在的目录；查询最多等待 30 秒并最多接收 64 KiB 输出。正常的单个行末换行会被移除；警告混入、多行结果、额外空白或非精确 SemVer 会在目标包暂存前失败。查询命令失败时会保留经过脱敏和限长的可操作原因，而不是只返回笼统的“无法查询包版本”。

目标目录暂存也会读取同一运行目录的项目级 `.npmrc`。更新器只在权限私有的临时目录中写入最多 1 MiB 的配置快照，随后由已验证的包管理器从该目录下载目标包，并在成功或失败后统一删除快照与暂存依赖；目录、设备或超限配置会在网络请求前被拒绝。这样企业镜像、作用域 registry 和代理设置不会在“版本查询成功、目录下载失败”之间悄然切换，同时不会改写生产 `.npmrc`。

更新目标目录与提供它的 OneBots 包根目录不可分离。无论目录来自当前安装、全局 CLI 邻近目录还是禁用安装脚本的临时暂存，只有同一根目录的 manifest 同时证明 `name: onebots` 和目标版本后，更新器才读取目录；因此一个安装的版本不能与另一个安装的目录拼接成更新证据。暂存包自报其他名称、错误版本或缺少清单时，即使包管理器成功退出也会在正式运行目录变更前失败。

自动化可以用 `onebots update --check` 做不修改生产运行目录的检查：当前组合已是目标版本时返回退出码 `0`，发现经过目标 OneBots 版本目录校验的更新时返回 `2`，版本查询、目录暂存或校验失败时返回 `1`。这样流水线无需解析自然语言输出，也能区分无需操作、应安排更新和检查本身失败。

`--check` 的已安装版本快照和“已是最新”判断也会取得共享包变更租约，并在租约内再次确认插件选择；因此它不会把扩展安装过程中的半成品或确认前的旧选择发布为自动化证据。网络版本查询与目标目录暂存发生在租约外，不会长期阻塞安装；取证时已有安装或更新进行中则明确失败并要求稍后重试。无需变更的 `--packages-only` 隔离预检会保持该短租约直到预检结束，保证被验证的依赖集合在子进程退出前不被替换。

**Kubernetes 配置示例**:

```yaml
livenessProbe:
  httpGet:
    path: /health
    port: 6727
  initialDelaySeconds: 30
  periodSeconds: 10

readinessProbe:
  httpGet:
    path: /ready
    port: 6727
  initialDelaySeconds: 5
  periodSeconds: 5
```

端口无法通过回环连接且没有已运行的受管服务时，doctor 还会用与网关启动相同的监听方式实际占用并立即释放该端口。其他网卡或 IPv6 上的占用以及绑定权限不足都会成为 `port` 错误，不再误报“端口可用”。

所有 `/health` 与 `/ready` 验证只读取最多 64 KiB 的响应正文，并同时检查声明的 `Content-Length` 与实际流式字节数。超限响应会立即取消读取并作为显式探针错误进入 doctor、status 以及 start/restart/update 的上线门禁；服务切换前记录旧 `instance_id` 的尽力探测也复用同一边界，而且只接受声明完整 `onebots` 应用身份、健康语义有效且 `runtime_contract_id` 与已安装服务元数据一致的实例。Web 管理端的公开身份预检、就绪探针和登录、刷新回执也采用 64 KiB 边界；公开响应超限时不会继续发送候选凭据，认证回执超限时不会替换已有会话。其余受保护的 Web 管理响应统一限制为 4 MiB，包括配置文本与 Schema、账号和系统快照、能力与扩展目录、安装、验证、消息历史、静态文件管理、备份、账号生命周期及重启回执；浏览器会按解码前流字节计数并取消超限正文，界面保留可解释的失败而不提交不完整结果。未知 HTTP 服务、旧端点或用其他启动参数运行的 OneBots 不会进入“进程已切换”证据。

共享 Router 会拒绝重复的 HTTP 方法与精确路径，并原子撤销数组路径等同一次注册产生的全部 Layer；WebSocket pathname 冲突也会在创建第二个服务前失败。账号作用域内的 HTTP 与 WebSocket 冲突错误都会同时指出正在注册和已经占用路径的平台与账号，便于直接定位多账号配置；同一 HTTP 路径的不同方法仍可分别注册。WebSocket 路由可用 `maxPayloadBytes` 限制单条入站消息，取值必须在 1 字节到 100 MiB 之间；未配置时仍使用原有的 100 MiB 上限，以保持现有协议与第三方扩展兼容。`maxConnections` 可进一步设置同一路径的正整数并发连接上限；Router 会先完成授权再检查容量，满载时在协议升级前返回 HTTP 503 与 `Retry-After: 1`，连接释放后立即恢复容量。未配置该选项的现有协议和扩展仍不限制连接数。管理端主连接限制为 32 条连接和 4 MiB 单消息，交互终端限制为 8 条连接和 1 MiB 单消息；超过入站消息上限的连接会在业务 JSON 或终端输入处理前以关闭码 1009 断开。`/metrics` 通过 `onebots_websocket_connections`、`onebots_websocket_connection_limit` 和 `onebots_websocket_capacity_rejections_total` 分别发布当前占用、配置容量和进程内累计满载拒绝；只使用固定的 `management`、`terminal` 标签，不枚举第三方扩展路径。管理主连接从建立时就接收入站动作，但会先放入暂停队列，待初始快照成功进入发送队列后再按到达顺序逐条执行，因此快照读取窗口不会丢消息，同一连接提交的配置保存和账号生命周期操作也不会并发交错；跨连接或跨传输的冲突仍由运行时配置事务和账号操作租约拒绝。每个连接最多保留 64 条、合计 8 MiB 的待处理动作；越界时清空等待项并以 1013 关闭，处理异常时以 1011 关闭，连接断开也会立即释放等待项。管理端的初始快照、配置与账号回执、实时日志以及终端输出也在进入发送队列前按 UTF-8 字节计数，分别沿用 4 MiB 与 1 MiB 的单消息上限；单个客户端的待发送数据最多为 8 MiB 或 2 MiB。出站单消息超限时以 1009 关闭，慢客户端达到缓冲边界时以 1013 关闭，不会让一个停滞页面持续占用进程内存。连续日志文件变更只保留一次正在执行的读取与一次最新重读，并对所有客户端复用读取结果。

`GET /api/adapter-capabilities` 提供独立于账号配置和扩展安装环境的完整平台能力证据。响应带 `schemaVersion`、生成时间、当前 OneBots 应用身份与 `instanceId`、目录完整性结论，以及已加载插件的运行时清单和未加载平台的版本绑定快照；因此零账号部署也能直接归档和比较平台。该管理端点同时在标准响应头和正文发布应用、版本、实例与运行契约身份，并使用 `no-store`；响应不会暴露插件的绝对入口路径。机器人页使用该端点而不再借用扩展安装清单，并在合并展示前要求响应头与正文身份完全一致，再与账号清单和扩展目录交叉验证；随后还会深度校验每份能力清单、声明状态、版本绑定、平台唯一性及顶层 `complete` 结论，`unavailable` 条目不能夹带可展示快照。扩展目录读取失败不会抹掉完好的已加载适配器；请求、身份或响应契约无效时会说明降级范围并提供重试，不会把畸形证据显示成确定支持。`onebots doctor` 的独立 `management-capability-catalog` 检查会从在线实例读取同一端点，先闭合响应头、正文与公开探针的实例及受管启动契约，再核对官方平台闭集、包名与固定版本、完整清单及其派生摘要；代理缓存或拼接的旧实例响应、缺失平台、伪造摘要、目录错误或无法绑定包版本的运行时插件都会使生产验证失败，同时不掩盖账号运行态检查。

能力目录请求失败、响应畸形或与账号运行态来自不同实例时，Web 会立即撤销上一次成功请求留下的目录快照，避免旧平台能力继续参与选型。只要 `/api/adapters` 自身仍通过身份与结构校验，机器人列表、账号操作和已加载适配器的运行时清单会继续可用；能力面板明确降级为仅展示这些运行时证据。能力目录故障不会再伪装成账号运行态故障，也不会让已有机器人从页面消失。

## 自动集成

所有生产就绪功能已在 `BaseApp` 中自动集成，无需额外配置即可使用。

### 自动启用的功能

1. **速率限制** - 默认 1 分钟 100 次请求
2. **安全审计日志** - 自动记录到 `{dataDir}/audit/`
3. **性能指标收集** - 自动收集所有 HTTP 请求指标
4. **健康检查端点** - `/health`, `/ready`, `/metrics`

### 可选配置

```typescript
import { App } from 'onebots';

const app = new App({
    port: 6727,
    log_level: 'info',
});

// App 已自动创建实例级管理会话存储，可通过 app.tokenManager 访问
await app.start();
```

## 注意事项

1. **速率限制存储**: 当前使用内存存储，生产环境建议使用 Redis
2. **安全审计日志**: 日志文件会按日期分割，建议定期归档
3. **性能指标**: 默认保留最近 1000 个样本，可根据需要调整
4. **令牌管理**: 令牌管理器需要手动初始化才能使用

## 后续优化建议

1. **Redis 支持**: 将速率限制和安全审计日志存储到 Redis
2. **分布式追踪**: 集成 OpenTelemetry 或 Jaeger
3. **告警系统**: 基于指标设置告警规则
4. **性能优化**: 添加缓存层和连接池优化
