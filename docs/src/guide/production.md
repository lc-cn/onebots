# 生产就绪功能

OneBots 提供了完整的生产级功能，包括安全性、稳定性和可观测性，确保系统可以在生产环境中稳定运行。

## 安全性功能

### 速率限制 (Rate Limiting)

防止 API 滥用，保护服务器资源。

**特性**:
- 基于时间窗口的速率限制
- 支持自定义键生成（默认使用 IP）
- 自动设置响应头（X-RateLimit-*）
- 集成安全审计日志

**默认配置**: 1 分钟 100 次请求

**自动启用**: 已在 `BaseApp` 中自动集成，无需额外配置

### 安全审计日志

记录所有安全相关事件，满足合规要求。

**特性**:
- 认证成功/失败记录
- 无效令牌记录
- 速率限制触发记录
- 可疑请求记录
- 错误事件记录
- JSON Lines 格式日志
- 按日期分割日志文件

**日志位置**: `{dataDir}/audit/security-audit-{date}.log`

**自动启用**: 已在 `BaseApp` 中自动集成

无效令牌审计与令牌生成、刷新、撤销日志不会保存 token 原文或明文前缀。需要关联同一进程内的事件时，日志只记录使用进程随机密钥生成的 16 位 HMAC 指纹；密钥不会写盘，进程重启后指纹会变化。该值只用于排障关联，不能作为令牌身份或鉴权证据。

### 管理面鉴权边界

`/api/*`、根管理 WebSocket `/` 与终端 WebSocket `/api/terminal` 使用同一组动态认证材料。普通管理 HTTP 只从 `Authorization: Bearer <token>` 读取凭据；`/api/auth/login` 可以在 JSON body 中提交顶层 `access_token`，也可以用用户名密码换取会话 token。日志、账号验证和消息调试 SSE 使用带 Authorization header 的 Fetch 流，不会把长期 token 写进 URL，并由同一客户端统一处理分帧、取消与有界重连。只有浏览器 WebSocket 握手可通过 `Authorization` 或 `?access_token=<token>` 传递，因为原生 WebSocket API 无法设置请求头。未授权 WebSocket 会在协议升级前返回 HTTP 401，不会先建立连接再关闭，因此无法收到包含完整配置的 `system.sync`。

Web 首屏仍兼容用 `?access_token=` 引导登录，但会先调用登录端点验证候选值，只有服务端确认后才写入本地会话。无效链接不会覆盖已有 token；已有会话会继续使用，尚未登录时则回到登录页说明凭据无效。登录、链接验证、令牌刷新和主动登出各自拥有 5 秒请求边界，超时、网络不可达、主动取消与凭据拒绝使用不同语义；慢代理不能让路由守卫、登录按钮或退出操作永久挂起。登出即使无法联系服务端也会清理浏览器本地凭据，服务端会话则在自然过期后失效。无论链接验证结果如何，下一次导航都会先从地址栏移除鉴权码。管理 HTML 还会同时通过 `Referrer-Policy: no-referrer` 响应头和前置的 referrer meta 禁止发送来源地址，因此脚本与样式在前端执行之前加载时，也不会把含 token 的入口 URL 复制到 `Referer` 请求头。建议人工集成优先在登录页输入鉴权码；根管理 WebSocket 的查询参数只用于无法设置 `Authorization` 请求头的客户端。

通过“保存并应用”轮换 `username`、`password` 或 `access_token` 后，HTTP 登录和 WebSocket upgrade 会立即使用新值。已有访问与刷新令牌会全部撤销，已连接的根管理与终端 WebSocket 会以策略违规状态关闭；日志、账号验证和消息调试 SSE 也会同步停止心跳并结束响应，旧会话无法在撤销后继续接收敏感事件。Web 会用当前本地凭据尝试重连，旧凭据被明确拒绝后回到登录页。只修改账号、协议或日志级别不会中断管理会话。正常停机与启动失败回滚复用同一管理流注册表，逐个释放定时器和响应；单个连接清理失败不会阻止其他连接关闭，最终错误会聚合保留失败证据。

用户名密码签发的会话 token 自然过期后，已建立的根管理与终端 WebSocket、日志、账号验证和消息调试 SSE 也不能继续被动接收数据。服务端每 30 秒重验一次长连接凭据，最迟在下一次检查时停止心跳并关闭连接。配置文件或 `ONEBOTS_ACCESS_TOKEN` 提供的部署级 token 没有会话过期时间，因此会保持连接，直到凭据轮换、服务停止或网络断开。

### 令牌管理

完整的令牌生命周期管理。

**特性**:
- 令牌生成和验证
- 令牌过期检查
- 令牌刷新机制
- 自动清理过期令牌
- 令牌撤销功能

**使用示例**:

```typescript
import { initTokenManager, createManagedTokenValidator } from '@onebots/core';

// 初始化令牌管理器
const tokenManager = initTokenManager({
    defaultExpiration: 3600000, // 1小时
    autoRefresh: true,
});

// 创建令牌验证中间件
const tokenValidator = createManagedTokenValidator(tokenManager);
```

### HMAC 签名验证

防止请求篡改和重放攻击。

**特性**:
- 支持多种 HMAC 算法（默认 SHA256）
- 时间安全比较
- 防止重放攻击

## 稳定性功能

### 熔断器模式

防止级联故障，提高系统韧性。

**特性**:
- 三种状态：关闭、开启、半开
- 基于失败次数和错误率的触发
- 自动恢复机制
- 状态监控和统计

**使用示例**:

```typescript
import { CircuitBreaker } from '@onebots/core';

const circuitBreaker = new CircuitBreaker({
    failureThreshold: 5,        // 失败阈值
    resetTimeout: 60000,        // 重置超时（60秒）
    halfOpenMaxCalls: 3,        // 半开状态最大调用数
});

// 使用熔断器执行操作
try {
    const result = await circuitBreaker.execute(async () => {
        return await externalService.call();
    });
} catch (error) {
    // 处理错误
}
```

### 重试机制

自动处理临时故障，提高成功率。

**特性**:
- 指数退避策略
- 随机抖动（防止惊群效应）
- 可配置重试次数和延迟
- 智能错误判断（只重试网络错误）

### 连接池

优化资源使用，提高性能。

**特性**:
- 连接复用
- 最大/最小连接数控制
- 空闲连接自动清理
- 连接验证
- 等待队列管理

## 可观测性

### 性能指标收集

自动收集系统性能指标。

**特性**:
- 计数器（Counter）
- 仪表（Gauge）
- 直方图（Histogram）
- 标签支持
- 时间窗口统计
- 自动清理过期数据

**自动启用**: 已在 `BaseApp` 中自动集成

### Prometheus 指标导出

标准格式的指标导出，可直接接入 Prometheus + Grafana。

**端点**: `GET /metrics`

**指标包括**:
- 应用信息（版本、运行时间）
- 内存使用（RSS、堆内存）
- 适配器、账号和协议出口状态
- HTTP 请求指标（请求数、响应时间、错误率）

**使用示例**:

```bash
# 访问指标端点
curl http://localhost:6727/metrics

# 配置 Prometheus
scrape_configs:
  - job_name: 'onebots'
    static_configs:
      - targets: ['localhost:6727']
```

### 健康检查端点

支持 Kubernetes 部署的探针。

**端点**:
- `GET /health` - 存活探针（liveness probe）
- `GET /ready` - 就绪探针（readiness probe）

**功能**:
- `/health`: 基础健康检查
- `/ready`: 检查服务、账号和每个协议出口是否就绪

宿主配置 `path: gateway` 时，所有 Router HTTP 路由统一挂载到规范前缀 `/gateway`，因此探针地址是 `/gateway/health` 与 `/gateway/ready`，管理 API 也位于 `/gateway/api/*`；根路径不再暴露这些 HTTP 路由。前缀可写成 `gateway` 或 `/gateway/`，启动时都会规范化为 `/gateway`。包含 authority、路径穿越、编码分隔符、查询串或 fragment 的值会被配置校验拒绝。WebSocket 使用独立的绝对 pathname，不继承 HTTP 前缀；管理 WebSocket 仍位于 `/`。`onebots status`、`doctor` 与服务上线验证会读取同一配置并自动使用规范后的 HTTP 地址。随主程序发布的 Web HTML 会在每次页面请求中注入当前进程的非敏感前缀元数据，并禁止缓存这份入口；登录、配置、扩展、探针和协议出口链接会自动使用它，无需用 `VITE_API_BASE` 重新构建 Web 包。构建期显式配置仍拥有最高优先级，畸形运行时元数据则退回同源根路径，避免把 Bearer 请求导向其他 origin。

普通管理 API 响应统一声明 `Cache-Control: no-store`，包括登录、令牌刷新、鉴权失败、账号与适配器清单、系统信息、配置正文和扩展状态。Web 管理端也为这些请求主动设置 `cache: no-store`，避免浏览器或错误配置的中间缓存复用旧运行态、旧配置或包含凭据的响应。日志等 SSE 长连接继续使用适合流式传输的 `no-cache`。

`/health` 的 `application` 与 `version` 表示实际运行的 `onebots` 主程序包，`core_version` 单独表示 `@onebots/core`。`instance_id` 在每次进程启动时生成，`started_at` 保留该进程的启动时间，可用于证明端口已经由新实例接管。Prometheus 的 `onebots_info` 使用主程序版本，`onebots_core_info` 使用 Core 版本；Web「系统信息」也会分别展示两者，避免升级后把依赖版本误认作在线应用版本。

`/ready` 同时携带与 `/health` 一致的 `application`、`version`、`core_version`、`instance_id` 和 `started_at`，因此单独保存一份就绪响应也能证明它属于哪个 OneBots 进程，而不是代理或其他应用返回的同名布尔值。其 `summary` 给出账号与协议实例总数、在线/就绪数量以及 `accounts_without_protocols`；每个平台也会列出缺少协议出口的账号数，以及协议的 `ready`、`unavailable` 与 `total`。即使平台账号已经 online，只要任一协议 `start()` 失败或任一账号没有协议出口，端点仍会返回 HTTP 503。响应中的 `config.status` 与 `config.in_sync` 还会证明磁盘配置是否就是当前运行版本；外部修改、不可读文件或等待重启的宿主配置会撤销 readiness。首次启动尚未配置账号时，管理面保持 HTTP 200 以便继续配置，但响应包含 `configured: false`，doctor 会把它明确标为警告。

Web 顶栏每 5 秒读取同一份 `/ready` 语义证据，区分「生产就绪」「待配置」「未就绪」和探针证据无效，而不再仅凭账号 online 数量显示绿色状态；点击状态可进入「系统信息」查看探针。系统页同时校验 `/health` 的应用身份、版本与实例标识，以及 `/ready` 自己的应用与实例身份、HTTP 状态、布尔结论、账号/协议计数和配置状态是否互相一致；两份响应的应用、版本或 `instance_id` 不同会显示“证据冲突”。因此代理返回的空 200、其他应用的响应、跨实例分流或矛盾 JSON 都不会被误报为可用。系统页的自动刷新每 10 秒同时更新受保护的进程信息与这对公开探针；自动周期和手动“刷新”会合并进行中的服务检查，慢请求不会叠加，5 秒未完成的系统信息与鉴权刷新会释放本轮任务供下一周期重试。各页面只启动自己实际使用的资源轮询，避免系统页、顶栏与机器人页重复请求同一清单。

热重载配置期间 HTTP 存活探针继续返回成功，但 `/ready` 会立即返回 HTTP 503 并声明 `reloading: true`，直到新账号与协议出口完成启动或旧配置完成回滚。首次进程启动仍会保留账号或协议启动失败的运行态，便于从管理面和 readiness 定位凭据、权限或平台故障；“保存并应用”则采用严格事务，任一适配器、账号或协议异步启动失败都会让应用操作失败，清理候选运行态并重新构造旧配置。旧运行态尚未完整停止时不会开始切换；若候选清理或旧运行态恢复也失败，最终错误会同时保留原始应用错误和回滚错误，不会把部分成功标记为已应用。外层配置保存边界随后恢复磁盘旧版本。并发热重载会被拒绝，防止两次配置切换交错覆盖。Prometheus 的 `onebots_reloading` 可用于记录和告警持续时间异常的重载。

部署或更新后可运行 `onebots doctor -c config.yaml --json --strict` 作为自动化门禁。JSON 使用带 `schemaVersion` 的稳定报告 envelope，并记录 `generatedAt`、当前 OneBots CLI 身份与版本，以及本次实际采用的配置路径、数据目录、解析后的数据库路径、扩展根、模块解析目录、服务范围和模式、适配器与协议列表及各自来源；CI 留档因此可以直接证明一次检查针对哪套安装和配置，无需解析人类可读消息。显式配置路径使前台或 Docker 部署执行独立配置诊断；若该路径就是托管服务保存的配置，doctor 仍会核验服务是否运行。独立诊断会像前台监听器一样让当前进程中非空的 `PORT` 覆盖 `config.port`，`onebots send` 也使用同一优先级，因此 Hugging Face 等托管环境不会探测或调用错误端口；无效的 `PORT` 会作为地址配置错误进入报告。已安装守护服务仍以保存的配置为准，不会把调用 doctor 时一次性的 shell 环境误认为服务定义。doctor 会把 `/health` 的在线主程序版本与当前 CLI 版本对比；不一致或旧端点无法证明版本时产生警告，严格模式会因此失败，能发现依赖已更新但旧进程尚未重启或命令入口指向另一套安装。默认模式仍允许首次配置流程继续，将未配置账号、服务未安装或已停止、无法完成合法管理凭据探测等状态保留为警告；`--strict` 会让任一警告同时令 JSON `ok` 为 `false` 并返回退出码 `1`。配置端口可连接时，doctor 会同时探测这两个端点；非 2xx、非 JSON、`status` 不是 `ok`、`ready` 不是 `true`，成功的 readiness 没有声明 OneBots 身份，或者两份探针来自不同应用版本或实例，都会让检查失败。独立的 `probe-instance` 检查在文本与 JSON 报告中保留成对身份结论。`/ready` 失败时，报告会列出在线账号、就绪协议数量、对应的未就绪平台以及缺少协议出口的账号，避免只看到一个没有上下文的 HTTP 503。Prometheus 可通过 `onebots_accounts_without_protocols` 为这类配置缺口设置告警。

若已安装服务的 `service.json` 被截断、无法读取或结构损坏，doctor 仍会生成完整 JSON 报告，将 `target.service.mode` 标记为 `invalid`，并以 `service-metadata` 错误阻止部署门禁通过。公开错误只包含元数据路径，不回显原始 JSON 片段；重新执行 `onebots install` 可按当前配置生成新的服务定义。在 POSIX 系统上，独立的 `service-metadata-mode` 还会验证这份运行契约没有向其他用户开放或允许同组修改；用户级 `--fix` 可恢复安装器约定的 `0600`，系统级元数据则只报告并交由管理员处理。

doctor 会分别验证当前 CLI 与守护服务定义中的 Node.js。对于服务保存的 `nodePath`，检查会实际执行 `--version`，因此路径虽然存在但不可执行、不是 Node，或版本低于 24 时都会产生 `service-node` 错误；用户级服务可通过 `--fix` 改用当前 doctor 的 Node 并重新生成定义，系统级服务则需要以管理员权限重新安装。

服务入口也不再以 `binPath` 存在作为充分证据。doctor 会解析符号链接后的真实文件，查找其所属 `package.json`，并确认包名是 `onebots`、版本与当前 CLI 一致且入口正是 manifest 声明的 `bin.onebots`。因此停止状态下仍能发现服务引用旧版安装、替代脚本或损坏清单；用户级 `--fix` 会改用当前 CLI 入口。

systemd unit、launchd plist 等平台服务定义无法读取或比对时不会再让 doctor 中断；`service-definition` 会以不包含文件内容的路径诊断令门禁失败。POSIX 上的 `service-definition-mode` 允许 unit/plist 公开读取，但拒绝组或其他用户写入；用户级 `--fix` 可恢复 `0644`，系统级只报告风险。安装器会原子替换定义并主动恢复 `0644`，因此重新安装也能消除既有危险权限。用户级 `--fix` 写入定义后会再次读取并与新元数据比较，只有结果一致才标记为 `fixed`。若 systemctl、launchctl 或任务计划程序在修复期间失败，doctor 仍会返回完整报告，保留修复前的 Node 与入口证据，并以定义路径报告失败，不回显底层命令可能携带的环境或文件内容。

Windows 用户级服务会同时验证任务计划 XML 与实际执行的 `onebots-user-runner.mjs`，包括 Node、CLI 入口、配置、插件选择、工作目录和日志输出。任务计划直接用 Node 执行 runner，不经过 `cmd.exe` 或 PowerShell；runner 以数组恢复完整参数，因此路径或配置值中的空格、`&`、`%VAR%` 和引号不会被 shell 解释。任一文件缺失或被修改都会让 `service-definition` 失败；重新安装或用户级 `doctor --fix` 会原子重建两份文件并清理旧 `.cmd` runner，再以同一渲染契约复验。卸载会移除任务 XML 与新旧 runner，但保留日志和用户数据。

Windows 系统级服务通过状态目录中的 `onebots-system-runner.mjs` 以数组无损传递完整参数，避开 `node-windows` 按空格拆分 `scriptOptions` 导致配置或入口路径失真的问题。WinSW XML 与 `.exe` 仍安装在 CLI 入口旁的 `daemon/` 目录；doctor 会同时验证 runner、Node、wrapper、工作目录、日志目录和重启策略。启动、停止与状态查询使用 WinSW 实际注册的 `onebotsgateway.exe` 服务 ID。任一文件或启动契约漂移都会失败并要求管理员重新执行 `onebots install --system`；卸载时会一并清理 runner。

服务安装本身也是事务。OneBots 先写入并注册候选平台定义，再按完整启动契约复验 unit、plist、任务 XML 或 WinSW 文件，最后才原子提交私有 `service.json` 元数据。平台命令、定义复验或元数据提交任一步失败时，已有安装会恢复上一份定义并再次复验；首次安装则撤销注册并清理候选定义与 runner，不留下无法由 CLI 管理的半安装服务。若恢复也失败，错误会同时保留原始安装问题与回滚证据，避免把受损旧服务误报为已恢复。

`service-permissions` 会验证保存服务元数据与日志的状态路径确实是当前进程可遍历、读取和写入的目录。普通文件占位、目录缺失或访问权限不足都会以只包含目标路径的错误令部署门禁失败，不会把原始文件系统异常带入报告。

账号管理摘要还会为每个协议出口返回 `name`、`version`、`path` 和 `lifecycleStatus`。机器人管理页会分别显示等待启动、启动中、就绪、停止中、已停止或失败，不再用账号 online 状态掩盖某个协议出口的启动失败。doctor 在验证合法管理凭据后会读取同一份受保护的运行态，直接报告 `平台.账号/协议.版本`；独立的 `management-capabilities` 检查会逐个验证适配器默认清单、账号级覆写和 `accountCapabilityErrors` 的闭合契约。仅声明 `capabilityDeclared` 却缺少有效清单、覆写不对应已配置账号、清单结构畸形、同一账号同时发布覆写与不可用诊断，或任一账号能力证据不可用，都会产生 `error`，使普通与 `--strict` 门禁失败，同时不掩盖账号和协议生命周期的独立结论。零账号时则明确报告已验证的适配器默认清单和“尚未配置账号”，不会用“0 个账号均可信”代替实际证据。公开的 `/ready` 仍只返回平台级聚合，不暴露账号标识。

同一次在线诊断还会验证管理面安全边界：匿名请求必须从 `/api/auth/me` 得到 HTTP 401，匿名根 WebSocket 必须在升级前得到 HTTP 401；随后使用配置中的 `access_token`（也支持 `ONEBOTS_ACCESS_TOKEN`）或用户名密码确认合法 HTTP 请求和 WebSocket 握手仍然可用。匿名 HTTP/WebSocket 会并行执行；取得凭据后，合法 HTTP、在线配置、运行态、账号能力与 WebSocket 探针也会并行执行，同时保持稳定的报告顺序。每项仍有独立的 2 秒边界，慢代理不会把所有超时串行累加。用户名密码探测生成的临时会话会在全部认证探针结束后注销。若自定义宿主只在内存中提供凭据、doctor 无法从配置或环境取得，匿名拒绝仍会验证，两项合法凭据探测则标为警告。

doctor 还会实际加载服务选用的插件，并使用它们注册的 Schema 校验完整账号和协议配置。每项成功结果会包含实际解析到的包名与版本，`plugin-selection` 检查会逐类别记录插件来自 CLI、配置文件还是服务定义，并给出模块解析目录。没有 `plugins` 的旧配置仍应传入与启动命令相同的 `-r` / `-p` 参数。

默认诊断已安装服务时，服务定义继续是实际运行契约。显式传入与服务定义不同的 `-c` 则表示验证一份独立候选配置：doctor 使用候选文件自己的插件默认值，不会把旧服务的插件混入结果，也不会因路径不同判定服务定义失效；即使同时传入 `--fix`，也不会改写那份无关的服务定义。这使发布流水线可以在切换服务前可靠验证下一版配置。

受保护的 `GET /api/system` 在 `plugins` 字段返回当前进程已通过入口加载和注册契约校验的适配器、协议及其包名、版本、真实入口路径；Web 管理端的「系统信息 → 运行时插件」展示同一清单。该信息来自正在运行的进程，可用于确认更新后是否已经重启到预期版本，也能区分同名插件实际来自哪个安装位置。管理 WebSocket 的初始 `system.sync` 同步相同数据。

setup、Web 管理端与运行时账号操作通过同一原子写入边界保存配置：新内容先在配置目录完成写入与同步，再替换正式文件，避免进程退出留下半截 YAML。Web 保存随后立即热重载账号与协议；应用失败会恢复磁盘和运行态的上一版本，宿主参数变更则返回需要重启的字段。单账号新增、编辑与删除也会同时锁住其他配置变更并撤销 readiness；只有账号启动或停止与配置落盘全部成功才会提交。新增和编辑会先把候选账号放入当前完整配置，复用启动时相同的适配器、协议及继承配置 Schema；缺少身份、平台凭据、已加载协议出口或字段类型错误会在构造适配器前以 HTTP 400 拒绝。平台登录、协议启动或写盘失败时，候选账号会被清理，旧账号、内存配置和磁盘文件会一起恢复；恢复本身失败时，响应会聚合原始错误与回滚证据。重复新增已有账号会被拒绝，配置事务冲突由管理 API 返回 HTTP 409，客户端可在当前操作结束后重试。更新已有配置时会把紧邻的上一版本保存在 `<config>.bak`；新配置默认权限为 `0600`，已有配置继续沿用原权限。恢复前仍应先用 `onebots doctor` 校验备份内容。

Web 扩展安装还会记录包管理器执行前的插件版本。包管理器成功后，若落盘版本校验、隔离预检或配置提交失败，OneBots 会通过同一个 npm/pnpm 反向恢复依赖：原来没有该插件时移除新增包，原来已有其他版本时精确装回，并再次读取包清单确认结果。恢复失败不会被掩盖，扩展中心的失败记录会同时保留原始安装错误和恢复错误，便于人工修复依赖与锁文件。

扩展安装按运行目录及其最近项目根的锁文件、workspace 声明和 `packageManager` 选择 npm 或 pnpm。即使 OneBots 从 pnpm workspace 成员目录被 `node` 直接启动，也会识别上层 workspace 并继续把依赖写入当前成员包，不会误用 npm 解析 `workspace:` / `catalog:`。独立 npm 项目仍优先采用自己更近的 `package-lock.json`。

发布工作流会真实打包所有公开包，并读取 tarball 内最终生成的 `package.json`。除入口与生产文件边界外，门禁还会拒绝残留的 `catalog:`、`workspace:`、`file:`、`link:`、`portal:` 或 `patch:` 依赖协议，避免 workspace 源清单在发布转换失败后形成 npm 无法安装的制品。

调用包管理器前，扩展中心还会验证运行目录确实属于当前 OneBots：项目清单必须自身为 `onebots` 或明确声明该依赖，目录内安装的包名和版本必须与当前进程一致。运行目录以及已有的 `node_modules` 也必须对当前进程可写；只读容器挂载或错误的目录属主会在启动包管理器前直接失败。OneBots 还会按该目录的锁文件、workspace 和 `packageManager` 选择 npm 或 pnpm，并证明对应入口存在于当前进程的 `PATH`；缺少 pnpm 时会提示安装或通过 corepack 激活。全局 CLI 从无关项目启动、`ONEBOTS_EXTENSION_ROOT` 指错目录、依赖尚未安装或旧版本 CLI 管理新目录时都会在读取配置和修改依赖前失败，并给出应切换目录或从目标目录启动的诊断。扩展清单 API 会提前发布同一错误，Web 只会禁用确实需要修改依赖的卡片；已安装且版本匹配的扩展仍可直接启用和预检。服务端安装端点会在读取配置和下载依赖前重新校验，不能靠旧页面绕过。`onebots doctor` 的 `extension-root` 与 `package-manager` 检查复用相同判断，并把结果写入文本和 JSON 报告；显式的 `ONEBOTS_EXTENSION_ROOT` 优先，否则使用守护服务或当前诊断的插件解析目录，因此错误、不可写或缺少包管理器的安装目标会直接使部署门禁失败。若 `config.yaml` 损坏或不可读，扩展清单会降级为未启用状态并发布脱敏的 `runtimeConfigError`，版本化平台能力仍可浏览；Web 会显示原因并禁用安装，服务端也会在下载依赖前以 HTTP 422 重新拒绝写操作。

Web「系统信息」、扩展安装流程和管理终端的重启请求共用同一安全边界：先执行服务工作目录中的插件与配置预检，响应返回后调用 `app.stop()`，让账号、协议、WebSocket 与 HTTP 资源按生命周期顺序释放，再以守护进程可识别的失败码退出。优雅停机超过 30 秒会记录错误并交由守护进程强制切换，避免重启永久挂起。系统页和扩展页必须先从 `/health` 取得应用身份为 `onebots` 的当前 `instance_id`，并把该身份随重启请求发回；服务端在预检和调度前拒绝已被其他实例接管的过期请求，成功回执则同时证明应用身份、处理请求的实例和调度状态。Web 验证完整回执后，只在端点恢复为不同的新实例时刷新。旧客户端可以继续省略请求身份，但仍会收到包含当前实例的结构化回执。每次 `/health` 与 `/ready` 探针都有独立的 2 秒超时，代理保持连接却不返回内容时也会留下明确证据并继续有限重试。仅有 HTTP 200、旧实例仍在线、空回执或身份字段缺失都不会被当作重启完成。

进程会在启动、每次成功热重载及账号配置落盘后保留配置文件的不可逆摘要。受保护的 `GET /api/system` 通过 `configState` 字段与 Web「系统信息 → 配置状态」只公开 `in_sync`、`drifted` 或 `unavailable` 及最近应用时间，不公开摘要或配置内容。若配置被外部编辑、挂载替换，或者 Web 保存的宿主字段仍等待重启，状态会保持 `drifted`；成功重新加载或重启后才恢复 `in_sync`。同一状态会投影到公开 `/ready`，不同步时返回 HTTP 503，并通过 `onebots_config_in_sync` 指标暴露为 `0`；doctor 会把漂移和文件不可读分别报告为可操作原因。管理 WebSocket 的初始 `system.sync` 也携带同一状态。

在 POSIX 系统上，doctor 会分别检查正式配置与 `.bak` 的权限。`0600` 视为私有；`0640` 等仅允许同组读取的模式会给出警告但不自动修改，以兼容服务账号共享；其他用户可访问或同组用户可修改会使检查失败。显式使用 `--fix` 时，这类高风险权限会收紧为 `0600`，JSON 报告中的 `fixed` 字段可供部署脚本留痕。

doctor 还会验证配置文件同级的 `data` 路径确实是当前进程可读取、写入和遍历的目录。默认数据库、安全审计和管理终端日志都使用该目录；守护服务与前台模式不会再按各自的当前工作目录分散日志缓存。若 `database` 使用绝对路径或通过相对路径离开默认目录，doctor 会继续验证解析后的实际数据库文件及其父目录，确保 SQLite 能创建 journal/WAL 文件；空路径、目录占位、不可读写文件或不可创建父路径都会使门禁失败。普通文件占位、错误的卷挂载或权限不足也会直接使默认数据目录检查失败，避免运行时存储初始化后置报错；数据目录缺失时默认给出警告，只有显式使用 `--fix` 才会创建并再次验证目录，既有冲突路径不会被替换。

`onebots setup` 与前台启动复用同一数据目录边界。首次初始化或 `setup --force` 会先验证或创建数据目录，再写入、备份配置；若挂载目标冲突或权限不足，命令会保留原配置、既有备份和冲突路径，避免显示失败后却留下已经生效的半套配置。非交互环境遇到已有配置时仍不会覆盖或创建备份，但会先验证 YAML、基础 Schema、适配器与协议配置及所选插件，并验证或创建同级 `data` 目录；只有现有配置具备实际启动条件才成功退出。直接启动缺少配置的目录时也会先通过这项验证，再生成默认配置与鉴权码。

“已加载”要求插件入口完成初始化，并注册 CLI 名称对应的工厂与配置 Schema。可导入但漏注册、名称不匹配或仅注册工厂而缺少 Schema 的插件会被 doctor 和所有服务预检判为错误，而不会延迟到启动后或 Web 管理端才暴露。

插件包身份也必须形成连续证据：候选目录中的 `package.json#name` 必须与实际请求的 npm 包名一致，固定版本校验和注册契约才会继续执行。目录被错误复制、替换或损坏时，入口代码不会运行；扩展中心会把该依赖标记为“无法验证”并显示期望包名与实际包名，重新安装时只使用当前 OneBots 目录锁定的包名和精确版本。包管理器即使成功退出，若落盘 manifest 自报另一身份，安装仍会失败并恢复安装前依赖。

Adapter 与 Protocol 注册表会在 Schema 首次注册时复制并递归冻结其对象、数组与正则表达式容器。插件随后改写原始对象，或通过 `getSchema()` / `getAllSchemas()` 尝试原地修改其他扩展的契约，都不会改变宿主实际使用的 Schema；同一原对象的重复注册仍保持幂等。数组和对象形式的默认值在每次配置校验时重新复制，因此不可变注册契约不会把冻结容器泄漏进账号运行配置。

适配器与协议的展示元数据也以冻结快照保存，`getMetadata()` 和 `getAllMetadata()` 不再暴露可改写的注册表内部对象。协议新增或移除版本时使用 copy-on-write 生成新的冻结版本列表，因此一个插件无法在加载事务结束后伪造其他插件的名称、来源信息或协议版本证据。

每次插件入口导入还会进入独立的异步注册时段。入口中的顶层 `await` 和导入完成前执行的异步任务仍属于本次事务，会统一接受注册归属检查与失败回滚；入口创建的定时器或 Promise 若在事务验收结束后才尝试注册、注销、清空或恢复 Adapter / Protocol 注册表，则会收到“插件注册事务已结束”错误，不能把迟到修改泄漏到已验证运行态。后续插件会获得新的注册时段，不受前一个插件关闭状态影响。

若入口已经成功求值，但随后因缺少 Schema、注册越界等契约问题被拒绝，OneBots 会让该入口在同一进程的下一次加载中重新执行，而不是复用 Node 的 ESM 成功缓存。这样修复或重新安装插件后可以直接重试；一旦某次事务通过验收，后续重复加载仍复用同一模块实例并保持幂等。

适配器实例创建时会把注册元数据中的默认能力清单与 `describeCapabilities()` 的默认结果逐项比对，并提前确认每个标为支持的动作都有具体实现。清单不一致或动作仍落到基类占位实现都会阻止启动，避免扩展中心的选型证据与账号运行态能力相互矛盾；未声明注册能力的第三方适配器仍按“能力未知”处理，不会伪造结论。

`GET /api/adapters` 与管理 WebSocket 会合并插件加载清单和账号运行态：适配器只要已经通过加载契约，即使尚未配置任何 Bot，也会返回注册名称、说明、插件版本和默认能力，并以空 `accounts` 明确表示“未配置账号”。机器人页因此可以直接比较已加载平台并进入账号配置，不会把零账号误判成“未安装适配器”。没有注册默认清单的第三方插件会返回 `capabilityDeclared: false`；Web 显示“能力未知”警告，空分类不能被解释为平台不支持，doctor 的 `management-capabilities` 也会失败并要求插件补充可信声明。

管理 API 发布账号能力前还会重新校验并复制冻结动态清单，再按结构内容与适配器默认清单比较。适配器即使为每个账号重新创建了内容相同的对象，也不会被误标为“账号专属清单”；真正不同的权限或订阅能力才进入 `accountCapabilities`。畸形清单和返回后被插件改写的对象不会成为 Web 能力证据。单个账号的动态清单读取或校验失败会记录适配器错误日志，并以 `accountCapabilityErrors` 返回长度受限的机器可读诊断，不会让整个 `/api/adapters` 或其他账号摘要失败；Web 会明确警告当前只是回退展示适配器默认清单，不能据此判断该账号的实际能力。

插件入口存在但初始化失败时，doctor 会保留底层首行错误，例如重复注册冲突或缺少运行时依赖，而不是只报告笼统的“初始化失败”。这类错误应先修复插件安装或命名冲突，再重新执行诊断。

使用 `onebots install -c config.yaml -r <adapter> -p <protocol>` 安装守护服务时，同一套插件加载与配置校验会在系统服务定义写入前执行。仅暴露 `exports.import` 的插件、顶层 `await`、Schema 校验和初始化异常都按前台启动语义处理；预检失败不会留下一个必然无法启动的服务。安装成功仍不会立即启动，可在审阅服务定义后执行 `onebots start`。

`onebots start` 与 `onebots restart` 还会读取已保存的服务定义，以安装时的 `workingDirectory` 解析插件，并重新校验当前配置。这能捕获安装后被删除或损坏的插件与配置；启动预检失败时不会请求操作系统启动服务，重启预检失败时也不会先停止现有实例。操作系统命令执行后，CLI 会在有限窗口内轮询 `/health` 与 `/ready`，要求在线应用名和版本与当前 CLI 一致、readiness 成功或处于可继续配置的首次部署状态，并要求两端声明同一个 `instance_id`。`start` 对已经在线的服务保持幂等；服务原本未运行但端口已被占用时，以及执行 `restart` 时，验证后的实例身份还必须不同于操作前。旧实例继续占用端口、两个探针分属不同实例、目标进程未上线或身份字段缺失时，命令返回失败并保留最后的探针证据，不会提前宣告启动成功。

`/health`、`/ready` 与 `/metrics` 都返回 `Cache-Control: no-store`，明确禁止浏览器和中间代理把瞬时运行状态当作可复用内容。doctor、status、启动/重启/更新验证以及终端仪表盘也以不可缓存请求读取探针；因此只要代理遵守 HTTP 缓存语义，部署门禁不会用旧实例的 `instance_id` 或旧 readiness 证明当前进程可用。终端仪表盘把 Web 页面 origin 与 Router HTTP 前缀分开处理：`o` 仍打开根页面，Health 则按规范化的 `path` 访问对应 `/health`。

`onebots ui` 终端运维面板中的启动、停止和重启键复用上述公开 CLI 命令边界。面板中的启动与重启同样先预检已保存的服务定义，并在操作后验证在线版本、readiness 与实例切换；失败原因会保留在面板中，而不会把底层进程管理器命令成功误报为服务可用。

`onebots stop` 会在发出停止命令后有限轮询进程管理器，只有服务不再处于运行状态才报告成功；超时会保留最后的状态证据。macOS 上的停止操作会用 `launchctl bootout` 从对应 launchd 域移除任务，阻止 plist 中的失败自动拉起策略把刚停止的进程重新启动；后续 `start` 或 `restart` 会重新 `bootstrap` 服务定义。终端运维面板的停止键复用同一验证。

前台与守护服务进程收到 `SIGINT` 或 `SIGTERM` 时共用有界优雅停机协调器：同一轮信号只调用一次 `app.stop()`，并释放账号、协议、WebSocket 与 HTTP 资源。正常关闭会取消 30 秒兜底并以成功状态退出；若关闭抛错，错误会记录且兜底继续生效，残留 SDK 或网络句柄无法再让进程永久挂起。关闭一直未完成时也会在超时后记录 fatal 日志并强制退出，交还控制权给进程管理器。

核心停机编排会隔离扩展失败：一个协议停止失败不会阻止同账号的其他协议与账号监听器，一个账号失败不会阻止同适配器的其他账号，一个适配器或生命周期钩子失败也不会跳过其余适配器、数据库、WebSocket/HTTP、安全审计与 `close` 监听器。数据库、Router、HTTP 等生命周期资源的释放失败也会在其他资源完成清理后进入最终错误，而不会被 `cleanupError` 日志掩盖。所有阶段完成后才汇总错误交给进程信号层，因此既保留可诊断的失败退出状态，也尽量避免强制退出前遗留资源。

启动同样采用完整回滚边界。配置校验、管理路由与日志监听初始化、生命周期钩子或 HTTP 监听任一阶段失败时，OneBots 会释放已创建的账号、协议、数据库、Router、WebSocket/HTTP、文件监听及进程级日志拦截，并把该 App 实例标记为不可再次启动。若回滚步骤也失败，最终错误会同时保留原始启动错误与回滚错误；守护进程后续重试会创建全新进程和实例，避免在半初始化对象上重复注册路由或监听器。

安全审计写流同样属于可等待的停机资源。`app.stop()` 与启动失败回滚会等待已排队的审计记录刷新并关闭文件描述符后才返回；写入目录被卸载、删除或失去访问权限时，流错误会进入同一停机失败汇总，而不会在临时目录清理或进程退出后以未处理异常迟到。重复关闭保持幂等，不会再次操作已释放的流。

管理终端日志也属于可等待的停机资源。正常关闭会先停止所有日志 SSE 心跳、结束客户端响应并恢复 `stdout` / `stderr`，再等待缓存写流彻底关闭后清空临时缓存，避免未完成写入在截断后重新出现。任一客户端或文件清理失败都在其他资源完成后进入停机错误；进程的同步 `exit` 监听只作为无法等待异步操作时的最后兜底。

服务启动后，`onebots status` 会同时显示进程管理器状态以及 `/health`、`/ready` 的语义结果，并打印独立的成对实例结论。输出会区分“运行中，已就绪”“运行中，待配置”“运行中，版本未验证”和“运行中，不可用”；在线主程序版本缺失或与当前 CLI 不一致、任一响应无法归属到具体 OneBots 实例、两个探针的应用版本或 `instance_id` 不同、服务已安装但未运行、任一探针失败时退出码为 `1`，服务未安装时为 `2`。首次未配置账号且两份身份一致时仍保持“待配置”并退出成功，便于继续使用管理面。因此 CI/CD 可以直接以 `onebots status` 作为轻量部署门禁，需要完整配置和插件诊断时再使用 `onebots doctor --json --strict`。

`onebots update` 默认读取当前 `config.yaml` 的 `plugins` 选择，因此通过 Web 扩展中心后装的适配器和协议也会进入版本检查与更新；显式 `-r` / `-p` 仍可按类别覆盖配置，旧配置没有 `plugins` 时才回退到服务安装时的快照。更新器只查询目标 OneBots 主程序版本；主程序有新版本时，会先在临时目录以禁用安装脚本的方式暂存目标包，读取它随包发布的扩展版本目录并清理临时内容。所有所选适配器和协议都使用该目录中的精确版本，不会各自追随 npm `latest` 组成未经共同验证的运行环境；目录缺项、格式损坏或暂存失败会在修改正式运行目录前终止。包管理器成功退出后，更新器会从项目运行目录读取包清单；全局 CLI 场景则回退到当前 OneBots 安装根，逐个确认主程序与所有所选插件的实际版本等于上述验证版本。项目级 npm 更新只保存生产依赖并使用 `--omit=dev`，不会在生产运行目录恢复开发工具；从 pnpm 启动 npm 时还会移除 npm 不支持的 pnpm 专用环境配置，避免 `_icqqjs-registry`、`recursive`、`store-dir` 等警告污染诊断。npm/pnpm 在 Windows 上统一使用 `.cmd` 入口。任一包缺失或偏离都会报告完整期望/实际清单，并在服务预检、定义改写和重启前终止。落盘版本全部可信后，才会从服务的 `workingDirectory` 启动更新后的 CLI 子进程，以同一插件列表执行无连接预检。只有新运行环境成功加载全部插件并通过配置校验，才会改写服务定义并按确认结果重启。重启后，更新命令会在有限重试窗口内同时探测 `/health` 与 `/ready`：两份响应必须声明同一个 `onebots` 应用、目标版本和 `instance_id`，该实例还必须不同于重启前，且 readiness 成功或仍处于允许继续配置的首次部署状态，命令才会报告完成；代理把两次请求分发给不同实例时会继续重试，并在超时错误中保留双方身份。交互模式选择暂不重启时，更新命令明确提示磁盘依赖已更新但运行中的仍是旧实例。版本落盘校验或新运行环境预检失败时不会停止当前实例，也不会替换服务定义；更新器会在这个安全窗口内通过同一 npm/pnpm 恢复全部所选包的原始精确版本、移除原本不存在的包，并逐包验证恢复结果。恢复本身失败时，错误会同时保留原始更新问题与恢复证据，要求人工修复依赖和锁文件。服务定义改写或进程切换开始后的失败则保留新版本，不进行可能破坏在线实例的盲目回滚。

包管理器落盘前，项目更新目录必须自身为当前版本的 `onebots` 包，或明确依赖且实际安装同版本 OneBots，并通过与扩展中心相同的可写性检查；只依赖 `@onebots/core` 的 SDK 或插件项目不会被误判为网关运行目录。由另一版本的全局 CLI 进入项目时也会在修改依赖与锁文件前失败，并提示从该项目的 OneBots 安装执行更新。损坏的子目录清单可以由上层可信项目收敛；若整条路径都无法提供可信项目，更新会停止，不会悄悄降级为全局安装。

更新目标目录与提供它的 OneBots 包根目录不可分离。无论目录来自当前安装、全局 CLI 邻近目录还是禁用安装脚本的临时暂存，只有同一根目录的 manifest 同时证明 `name: onebots` 和目标版本后，更新器才读取目录；因此一个安装的版本不能与另一个安装的目录拼接成更新证据。暂存包自报其他名称、错误版本或缺少清单时，即使包管理器成功退出也会在正式运行目录变更前失败。

自动化可以用 `onebots update --check` 做不修改生产运行目录的检查：当前组合已是目标版本时返回退出码 `0`，发现经过目标 OneBots 版本目录校验的更新时返回 `2`，版本查询、目录暂存或校验失败时返回 `1`。这样流水线无需解析自然语言输出，也能区分无需操作、应安排更新和检查本身失败。

**Kubernetes 配置示例**:

```yaml
livenessProbe:
  httpGet:
    path: /health
    port: 6727
  initialDelaySeconds: 30
  periodSeconds: 10

readinessProbe:
  httpGet:
    path: /ready
    port: 6727
  initialDelaySeconds: 5
  periodSeconds: 5
```

## 自动集成

所有生产就绪功能已在 `BaseApp` 中自动集成，无需额外配置即可使用。

### 自动启用的功能

1. **速率限制** - 默认 1 分钟 100 次请求
2. **安全审计日志** - 自动记录到 `{dataDir}/audit/`
3. **性能指标收集** - 自动收集所有 HTTP 请求指标
4. **健康检查端点** - `/health`, `/ready`, `/metrics`

### 可选配置

```typescript
import { App } from 'onebots';
import { initTokenManager } from '@onebots/core';

// 初始化令牌管理器（可选）
const tokenManager = initTokenManager({
    defaultExpiration: 3600000, // 1小时
    autoRefresh: true,
});

const app = new App({
    port: 6727,
    log_level: 'info',
});

await app.start();
```

## 注意事项

1. **速率限制存储**: 当前使用内存存储，生产环境建议使用 Redis
2. **安全审计日志**: 日志文件会按日期分割，建议定期归档
3. **性能指标**: 默认保留最近 1000 个样本，可根据需要调整
4. **令牌管理**: 令牌管理器需要手动初始化才能使用

## 后续优化建议

1. **Redis 支持**: 将速率限制和安全审计日志存储到 Redis
2. **分布式追踪**: 集成 OpenTelemetry 或 Jaeger
3. **告警系统**: 基于指标设置告警规则
4. **性能优化**: 添加缓存层和连接池优化
